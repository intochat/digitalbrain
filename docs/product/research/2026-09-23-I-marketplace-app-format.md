# I-marketplace-app-format

## Summary
Established platforms handle third-party apps in broadly the same way, and IntoChat has none of those pieces yet. The common pieces are:
- **Manifest:** a declarative file with a publisher-namespaced id, a SemVer version, an engine range, entry points, activation triggers, required and optional permissions, dependencies and pricing (VS Code, Chrome MV3, the Microsoft 365 manifest, MCP server.json, Claude plugin.json).
- **Packaging:** a signed package, with the listing metadata kept apart from the code (the MCP Registry stores metadata and points to npm, NuGet or OCI packages).
- **Permissions:** asked for at install, with fewer permissions to start and more requested at runtime. Updates that add permissions need the user to accept again (Chrome disables the extension until accepted; Teams won't auto-update).
- **Confirmation before risky calls:** the MCP spec says hosts SHOULD keep a human in the loop, and M365's `confirmation` object can mark read-only calls as safe to "Always allow".
- **Trust tiers:** automated scans, then a verified publisher, then optional human certification, plus a kill switch that uninstalls apps already installed.

Agent-era formats (OpenAI Apps/MCP Apps, M365 declarative agents, Android AppFunctions, Apple App Intents, Claude Skills) add two things. First, the function schema and model-facing descriptions are generated at build time from code. Second, the assistant sees only a short summary of each app at first and loads the details when it is needed.

**IntoChat today (repo evidence):**
- **Modules have no manifest.** They are chosen when the AppHost is compiled (`WithModule<T>()`). A module's identity is its CLR type name, with no version or publisher. `IModule` gets the full `ISiloBuilder`. So installing an app currently means rebuilding the AppHost.
- **User-authored behaviors run with full access.** They do run in a separate process, but that process can reach any neuron. `BehaviorScopedBrain.Get` passes every id straight through. The job object only kills the process when the job closes; it sets no memory, CPU or network limits. The agent prompt says "Code nodes run trusted local C#", and the only approval step is wording in that prompt.
- **Capability discovery doesn't scale.** It reflects over assemblies, allows at most 32 modules and cuts the list off at 24,000 characters.
- **Useful groundwork exists:** stable `[Alias]` ids, 100 `[ReadOnly]` methods, a preview-then-confirm write pattern in Salesforce, deploy and rollback with revisions for behaviors, `[Description]` attributes on MCP tools, and Contracts projects that already build as NuGet packages.

**The biggest engineering constraint:** modern .NET has no security boundary inside a process. Code access security is gone, and Microsoft's docs say `AssemblyLoadContext` "does not provide any security features" and "Untrusted code cannot be safely loaded into a trusted .NET process". So third-party neurons must never load into the core silo.

**Recommended app format:**
- **Package:** a signed NuGet `.nupkg` with a custom `IntoChatApp` package type and an embedded `intochat/app.json` manifest. This copies the way NuGet already ships MCP servers (`McpServer` package type plus an embedded `.mcp/server.json`).
- **Three runtime kinds:**
  - **Declarative:** a manifest that combines existing neurons with UI and skills, with no code. This is the path for non-programmers, and it matches Power Platform solutions, GPTs and Glide templates.
  - **Sandboxed process:** a code app in its own process, reaching other neurons only through a broker grain that checks every call against the manifest.
  - **WebAssembly components:** a later option. They give capability-based isolation and "fuel" metering, which maps well onto Compute, but the C# toolchain says it is "under heavy development".
- **Discovery:** index each app's name, model-facing description, functions, example prompts and scenarios in the existing Qdrant memory. Load details only when the assistant needs them, the way Claude Skills do (about 100 tokens of metadata always, full instructions on demand).
- **Pricing:** declare Compute tariffs in the manifest as meter dimensions, modelled on Microsoft Marketplace metering: immutable id, unit, price per unit, included quantity. Charge only against a spending cap the user approved, as Shopify does with `cappedAmount`.
- **Trust pipeline:**
  - prove the publisher owns its namespace;
  - scan the package (schema, banned APIs, secrets, malware, dependencies);
  - run it in a sandbox, compare the permissions and Compute it actually uses with what it declared, and measure precision and recall on its example prompts;
  - send it to human review only when it asks for risky permissions;
  - on install, show a consent screen with permissions, meters and the cap; ask again whenever an update adds permissions; keep a blocklist and rollback.

Assistant-generated C# is exactly the "remotely hosted code" that Chrome MV3 bans for reviewability. So it should stay private to its author until someone re-publishes it through the same pipeline.

**Confidence:** high for platform facts fetched from primary docs and for the repo facts. Medium for the OpenAI Apps SDK, whose docs now say "Plugins" and whose pages were partly unavailable. Low to medium for Salesforce and GPT Store fees, which come from search summaries because the primary pages returned 403.

### I1 (gap, high) Modules have no manifest and are chosen when the AppHost is compiled
A module is identified by its CLR type full name, with no version, publisher, permissions or description. IModule gets the full ISiloBuilder and endpoint router, so a module can register anything in the silo. Modules are added in AppHost.cs with WithModule<T>(), so adding an app means recompiling and restarting the AppHost. There is no install-at-runtime path, no namespace and no version. The Contracts projects already build as NuGet packages (IsPackable=true), which makes NuGet a natural container, but the package carries no app metadata.

### I5 (pattern, high) Fields the manifests have in common
Across platforms the manifest holds: (1) identity: publisher plus name, or a reverse-DNS namespace (VS Code publisher.name; MCP io.github.user/name; M365 GUID id); (2) SemVer version (M365 n.n.n); (3) engine compatibility (VS Code engines; Chrome minimum_chrome_version); (4) display metadata: name, description, icons, categories, keywords, localization; (5) contributions/entry points (VS Code contributes; Chrome action/background/content_scripts; M365 copilotAgents/extensions; Claude skills/agents/hooks/mcpServers); (6) activation triggers (VS Code activationEvents, implicit from contributions since 1.74, '*' discouraged); (7) required and optional permissions (Chrome permissions/optional_permissions/host_permissions; M365 authorization; VS Code capabilities.untrustedWorkspaces); (8) dependencies (VS Code extensionDependencies; Claude dependencies with semver ranges); (9) pricing (VS Code pricing Free/Trial); (10) config, including secrets (Claude userConfig with sensitive:true; MCP environmentVariables isSecret); (11) privacy and support URLs (M365 plugin privacy_policy_url).

### I6 (pattern, high) How permissions and consent work: declare up front, grant little, ask again when an update adds more
Chrome MV3: four keys (permissions, optional_permissions, host_permissions, optional_host_permissions). Warnings are shown at install, and 'the extension will be disabled until the user accepts the new permission' when an update adds a warned permission. Teams: apps auto-update unless the update adds or removes permissions or changes webApplicationInfo, which needs consent. M365 plugin functions declare a confirmation object; isNonConsequential enables 'Always Allow'. MCP spec: hosts SHOULD keep a human in the loop and show confirmation prompts, and 'clients MUST consider tool annotations to be untrusted unless they come from trusted servers'. Shopify protected customer data: Level 1 vs Level 2 (name/email/phone/address), granted only when 'the requested data is the minimum amount required'. Power Platform DLP: connectors grouped as Business, Non-business or Blocked, and one app/flow cannot mix groups, which blocks data moving across them. For IntoChat: typed sensitive data (date of birth, password) needs data-class permissions, not just neuron-level ones.

### I7 (fact, high) .NET has no in-process sandbox, so third-party neurons cannot be loaded into the core silo
Code access security and security transparency are unsupported as security boundaries in .NET 6+. Microsoft advises using virtualization, AppContainers, OS users or Hyper-V containers instead. The AssemblyLoadContext docs say it 'does not provide any security features. All code has full permissions of the process'. The plugin tutorial says 'Untrusted code cannot be safely loaded into a trusted .NET process.' So an app package can be a NuGet package, but its implementation assembly must run behind a process, container or Wasm boundary. Only its contracts assembly (interfaces and records) may be loaded by the host, and ALC should be used only for version isolation, never for security.
Evidence: https://learn.microsoft.com/dotnet/standard/security/secure-coding-guidelines; https://learn.microsoft.com/dotnet/core/porting/net-framework-tech-unavailable#code-access-security-cas; https://learn.microsoft.com/dotnet/api/system.runtime.loader.assemblyloadcontext?view=net-10.0; https://learn.microsoft.com/dotnet/core/tutorials/creating-app-with-plugin-support

### I8 (risk, medium) WebAssembly components fit the model well, but the C# toolchain is not mature enough for v1
In the component model, 'a component interacts with a runtime or other components only by calling its imports and having its exports called', and components cannot share memory. That is capability-based by construction: an app gets only the neuron capabilities the host passes in. Wasmtime isolates via imports/exports and guard regions. Its fuel feature 'deterministically' traps runaway code, which could meter Compute directly; epoch interruption is up to 2-3x faster when determinism is not needed. Shopify Functions show the pattern in production: Wasm modules, JSON in and out, no network, called only by the platform. However, componentize-dotnet says: 'All the underlying technologies are under heavy development and are missing features.' Recommendation: design the capability broker so a Wasm runtime kind can be added later, and ship v1 with process isolation.
Evidence: https://component-model.bytecodealliance.org/design/why-component-model.html; https://docs.wasmtime.dev/security.html; https://docs.rs/wasmtime/latest/wasmtime/struct.Config.html (consume_fuel, epoch_interruption); https://shopify.dev/docs/apps/build/functions; https://github.com/bytecodealliance/componentize-dotnet/blob/main/README.md

### I9 (pattern, high) Agent-era app formats generate function schemas and model descriptions at build time
Android AppFunctions: '@AppFunction' plus an annotation processor generates an XML schema that the OS indexes; KDoc becomes the model-facing schema (isDescribedByKDoc); only callers holding EXECUTE_APP_FUNCTIONS can discover or execute functions. Apple App Intents: 'During compilation, the compiler generates information that Apple Intelligence, Siri ... need to discover' intents and entities; there is no runtime registration. M365 API plugin: functions with parameters, returns, states and capabilities (confirmation, response_semantics, security_info). MCP tools: inputSchema, outputSchema and annotations. MCP Apps: tools link UI through _meta.ui.resourceUri to a ui:// resource (text/html;profile=mcp-app) with declared CSP domains and visibility ['model','app']. For IntoChat: generate the functions section of app.json from neuron interfaces with a source generator ([Alias], [ReadOnly], [Description]) so declarations cannot drift from code.

### I10 (pattern, high) Discovery: show a short summary first, load details on demand, and test with example prompts
Claude Agent Skills: metadata (name at most 64 chars, description at most 1024 chars, and it must say what the skill does and when to use it) is always loaded at about 100 tokens per skill; instructions under 5k tokens load when triggered; resources load when accessed. So many apps can be installed 'without context penalty'. OpenAI metadata guidance: 'ChatGPT and Codex decide when to call your tool based on the metadata you provide'; start descriptions with 'Use this when…'; build a golden prompt set of direct, indirect and negative prompts; track precision and recall, fixing precision on negative prompts first. For IntoChat: embed each app's descriptionForModel, function descriptions, examples and scenario titles in the existing Qdrant memory; give the assistant only the top-k summaries; fetch full contracts on demand. This replaces ContractCatalog's 24k-character truncation (I3). Make the golden-prompt precision/recall check a review gate.

### I11 (pattern, high) Keep the catalog (metadata and ranking) separate from the package store (code)
The MCP Registry 'hosts metadata that points to those packages' (npm, PyPI, NuGet, OCI). It proves namespace ownership through GitHub, DNS or HTTP challenges and leaves security scanning to the package registries and curation to downstream aggregators. NuGet already supports this for agent tools: an 'McpServer' package type plus an embedded .mcp/server.json, searchable on nuget.org with packagetype=mcpserver; the registry checks an mcp-name marker in the README. Claude plugin marketplaces are just a marketplace.json listing sources (GitHub ref+sha, npm, zip with sha256); Claude verifies archive hashes; enterprises can allowlist marketplaces (strictKnownMarketplaces). For IntoChat: NuGet (a private feed, or nuget.org later) stores the code; an IntoChat catalog service holds manifest metadata, vectors, ratings, verification status and blocklist.

### I12 (fact, high) A NuGet package can hold an app, but signature checking must be set to 'require'
NuGet supports custom package types ('<packageType name="ContosoExtension" />', optionally versioned). It has author signatures (content unchanged since signing, whatever the source) and repository signatures (nuget.org repository-signs every package). signatureValidationMode=require with trustedSigners (author fingerprint or repository plus owners) blocks unsigned or untrusted packages. Caveats: 'Packages signed with untrusted certificates are considered as unsigned and are installed without any warnings' in the default mode. Author signing is supported only by nuget.exe on Windows. nuget.org rejects self-issued certificates. ID prefix reservation rejects other owners' packages under the prefix and shows a verified check mark. For IntoChat: the IntoChat installer should always run in require mode, trusting the IntoChat catalog's repository certificate, and apply its own repository signature when a package passes review.
Evidence: https://learn.microsoft.com/nuget/create-packages/set-package-type#custom-package-types; https://learn.microsoft.com/nuget/reference/signed-packages-reference; https://learn.microsoft.com/nuget/consume-packages/installing-signed-packages; https://learn.microsoft.com/nuget/nuget-org/id-prefix-reservation#id-prefix-reservation-details

### I13 (pattern, high) Review and trust tiers: automated scans for everyone, publisher verification, human review for risky apps, kill switch
VS Code Marketplace: signs every extension at publish and verifies on install; multi-engine malware scan on every version; 'dynamic detection by ... running it in a sandboxed environment'; secret scanning blocks publishing; name-squatting protection; a 'trust this publisher' prompt on first install; verified badge requires a domain TXT record plus 6 months of Marketplace and domain history; malicious extensions are blocklisted and 'automatically uninstalled'. VS Code's lesson: 'The extension host has the same permissions as VS Code itself', and signing plus scanning still let malware through, which is why IntoChat also needs runtime isolation. Chrome: human plus automated review; broad host or sensitive permissions lengthen review; obfuscation disallowed; malware leads to permanent account suspension. Teams Store: 400+ test cases; Graph permissions checked against actual functionality; publisher verification required; attestation (80+ factors, renewed yearly); optional M365 Certification with an external audit. Salesforce: security review required to list a managed package, with Code Analyzer reports. Zapier: every trigger/action tested in live Zaps, then a 90-day public beta.

### I14 (risk, high) Assistant-generated C# is the 'remote code' that Chrome's MV3 rules ban
Chrome MV3: 'all of your extension's logic must be part of the extension package. You can no longer load and execute remotely hosted files'; remote JSON config and data are allowed. The reason is that reviewers must see the exact code users run. IntoChat's assistant compiles and deploys new C# at runtime (program_compile, 'Code nodes run trusted local C#'), and it can change after any review. Recommendation: keep assistant-authored code private to its author, sandboxed, and unable to charge other users Compute. Sharing it or listing it in the marketplace means publishing a frozen, signed version through the full pipeline. Where possible, non-programmers should produce declarative apps (compositions of reviewed neurons, UI and skills) rather than code.

### I17 (recommendation, high) Declare Compute tariffs in the manifest as meter dimensions, and charge only within a user-approved cap
Microsoft Marketplace metering is a ready template. A dimension has an immutable identifier, display name, unit of measure, price per unit and included quantity; there is a maximum of 30 per offer, and identifiers can't be edited after publishing. Usage is reported as at most one event per hour per resource per dimension, within 24 hours, with duplicates rejected. Shopify adds the consent side: usage charges require merchant approval of a cappedAmount through confirmationUrl, and a webhook fires at 90% of the cap. For IntoChat: app.json 'meters' = [{id, displayName, unit, priceCompute, includedPerMonth}]. The platform broker, not the app, records usage for each function call a meter covers, keyed by the existing operationId pattern for idempotency. LLM tokens and storage are first-party meters from the platform itself. Install consent shows the meters and asks for a monthly cap; raising a price or adding a meter triggers consent again (I6/I15).
Evidence: https://learn.microsoft.com/partner-center/marketplace-offers/azure-app-metered-billing#billing-dimensions; https://learn.microsoft.com/partner-center/marketplace-offers/marketplace-metering-service-apis#metered-billing-single-usage-event; https://learn.microsoft.com/partner-center/marketplace-offers/create-new-saas-offer-plans#define-a-pricing-model; https://shopify.dev/docs/apps/launch/billing/subscription-billing/create-usage-based-subscriptions; src/Applications/IntoChat/IntoChat/Apps/AppContracts.cs:20-22 (expectedRevision, operationId parameters)

### I18 (pattern, medium) Non-programmers publish combinations of reviewed building blocks, not code
Power Platform: apps are packaged as Solutions. Unmanaged solutions are developed; managed solutions are deployed as build artifacts and cannot be edited, and uninstalling removes their components and data. A publisher prefix prevents name collisions, and the publisher cannot be changed later. Admins control which connectors can be combined through DLP. GPTs are built by 'typing in a natural language chatbot-style interface'. Glide sells copy-and-customize templates, re-submitted as new versions. Airtable Extensions are built with the Blocks SDK and listed after submission. Zapier requires live-tested triggers and actions and Zap templates. For IntoChat: a 'declarative' app kind (manifest plus bindings to existing neurons, UI parts, skills and prompts, with no executable code) is the safe way for regular people to build LeadGenerator-style apps, and is cheap to review.

### I19 (gap, medium) No BDD feature files exist, so the owner's idea of discoverable Reqnroll features has nothing to start from
A glob for src/**/*.feature returns nothing (per project memory, the BDD lane was deleted earlier). Other platforms use executable scenarios as a review gate rather than as the discovery index: Zapier requires every trigger/action to have run in a live Zap; OpenAI recommends golden prompt sets scored on precision and recall. For IntoChat: ship features/*.feature (or plain example-prompt lists) in the app package. ### I21 (recommendation, medium) Recommended runtime: three app kinds behind one broker that enforces permissions
(a) declarative: no code; the platform runs the bindings, UI and skills; available to non-programmers through the assistant. (b) process: the app's neurons run in a per-app OS-isolated worker (container or AppContainer, a job object with memory, CPU and process limits, no direct Orleans gateway, network denied unless listed in permissions.network). It reaches other neurons only through a broker grain that checks every call against the manifest (alias pattern, method, dataClass) and records meters. This replaces today's pass-through BehaviorScopedBrain.Get (I2). (c) wasm: later, with fuel mapped to Compute (I8). First-party modules (the current src/Modules) stay in-silo and trusted, but should also carry an app.json so discovery, consent and Compute handling are the same for all apps. Consent UX: an install sheet showing permissions, data classes, meters and a monthly Compute cap; per-call confirmation for functions not marked readOnly/non-consequential, with 'Always allow' for read-only calls; consent again on permission or meter increases. Governance: a per-app identity in traces and audit logs (this also helps with the Aspire trace clutter), a blocklist that disables apps already installed, and org or admin allowlists.

## Open questions
- Who may publish in the first marketplace release: first-party only, invited developers, or also non-programmers building through the assistant? This decides whether the declarative and process app kinds are both needed on day one.
- Do third-party code apps run on the user's own machine (desktop cluster), only in a hosted cloud, or both? The sandbox choice (Windows AppContainer/job objects vs Linux containers vs Wasm) depends on it.
- Revenue model: the platform's cut (e.g. 0% up to a threshold then 15%, as Shopify does; or a flat 3%, as Microsoft does), whether developers can cash out Compute or only spend it, and who sets Compute's exchange rate and the per-model LLM prices.
- Is billing through the platform mandatory for listed apps (Shopify rule), or may apps charge users directly (external checkout, as in ChatGPT)?
- Distribution channel: a private IntoChat NuGet feed only, or also nuget.org with an IntoChatApp package type and reserved prefix? And is the catalog also exposed as an MCP-registry-compatible API?
- Can assistant-authored behaviors ever be shared or sold? If yes, is it acceptable that sharing always means freezing, signing and running the full review pipeline, with no live-edited code shared across users?
- How fine-grained should permissions be in v1: per neuron alias and method, per data class (date of birth, password, email), per network host, or a smaller set of coarse scopes that is easier for regular users to understand at consent time?
- Should apps be allowed to make outbound network calls (e.g. BackgroundRemover calling an external API)? Deny by default with a declared host list, or allow only calls through first-party connector neurons?
- Is tenant/admin governance (allowlists, blocking apps, approving updates) needed in the first release, or is it single-user only?
- Should human review be required for every listing, or only for apps above a risk threshold, and who staffs it?
