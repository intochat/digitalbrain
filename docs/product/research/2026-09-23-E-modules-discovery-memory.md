# E-modules-discovery-memory

## Summary
The pieces of a package system exist: modules, a contract catalog, a Qdrant memory module and runtime-compiled behaviors. They are not connected in a way the assistant can discover or that a third party could install. Each module is split into four projects (Contracts, implementation, Aspire.Hosting, Tests). The AppHost declares modules with `WithModule<T>()` and passes them to the silo as environment variables of the form "Type, Assembly". The silo then loads them with `Type.GetType`, which only works for assemblies compiled into IntoChat. Adding a module means editing AppHost.cs, AppHost.csproj and IntoChat.csproj, rebuilding and restarting the cluster. There is no manifest, version, description, permission set or per-workspace install. The 50 packable projects share one version (0.1.0-alpha.1, net11.0). CI only runs `dotnet pack` as a check: nothing is signed and nothing is published to a feed.

The assistant cannot search the system. The IntoChat `/agent` endpoint gives the model a fixed list of 16 tool names (2 Supabase and 14 behavior/coding tools) plus one long instruction string. `AgentTurnRunner` accepts only exact names, with no ranking or search. Several modules are installed but no chat tool reaches them: ClickHouse (seeded with "leads"), Memory, Salesforce, Gmail, GitHub, Aspire, Roslyn and DotNet. The closest thing to discovery is the `code_contracts` tool. It uses reflection over four hard-coded contract DLLs (time, flutter, ai, google), returns flat signature strings and cuts the list off at 24,000 characters. It shows parameter types but not allowed values. That is why the owner's card with a "date" field failed: TextField accepts only text, number, password and suggest, and that list lives only inside TextFieldNeuron.

A capability index was built and removed twice. On 1 Aug 2026 capabilities were written into Qdrant under the reserved namespace `digitalbrain.capabilities`. On 10 Aug that was replaced by an in-process hybrid index, because the Qdrant version caused a 10-second stall and retry storms. On 20 Aug the whole "generic agent capability system" was deleted (about 2,400 lines). The Memory module today is a plain note store: `IMemory` offers Remember, Forget and Recall over one cosine collection, `digitalbrain_vector_memory`. It uses text-embedding-3-small (1,536 dimensions) as configured in the AppHost. Nothing in IntoChat calls it, and the Qdrant container has no data volume. Contracts carry no descriptions (no `[Description]` attributes, no XML docs, only 3 module READMEs), and there is no registry of neuron instances. So indexing "every neuron, namespace, method, signal, UI part and behavior" first needs a metadata source and an instance catalog. The storage side is small: fewer than 5,000 vectors.

The closest things to an "app" are:
- **Local apps:** Files and Image Editor are hand-written C# neurons and REST routes. The Flutter shell hard-codes the list files/images/behaviors.
- **Behaviors:** runtime-authored C# that is compiled, tested, sealed into a hashed artifact and supervised in its own process, with rollback. This is the only thing that can be added without redeploying, but it runs with the host OS user's privileges, only on Windows, and on a single host.

The declarative app-definition model in docs/intochat-neuron-app-composition.md is explicitly marked as not implemented. A marketplace package would additionally need a manifest, a permission model, isolation, versioning, signing, install and uninstall without restarting the cluster, per-user or per-workspace scope, and pricing hooks.

Stale or broken items also make the product hard to understand:
- CONTEXT.md describes things that no longer exist in code (IHandle, synapses, journals, IAspire).
- 13 IntoChat files are excluded from compilation.
- ConversationalAgent is never called.
- The Kernel "brain" MCP server is not hosted and would fail if started.
- A fake Twitter module is installed in the product AppHost.
- CI paths point at a Flutter folder that has moved.

I could not use live Aspire resource data: the tool output was saved under C:\Users, which I am not allowed to read. Everything here comes from source and git history.

## Findings

### E1 (fact, high) [VERDICT: confirmed] Modules load by CLR type name from compile-time references; adding one needs three file edits, a rebuild and a restart
`IModule` has only `Configure(ISiloBuilder)` and `Configure(IEndpointRouteBuilder)`. The AppHost declares modules with `builder.AddDigitalBrain(...).WithModule<T>()`. `WithReference(brain)` passes them to the silo as environment variables of the form `DigitalBrain__Modules__{i}` = "FullName, AssemblyName". The silo resolves each with `Type.GetType(name, throwOnError: true)` plus `Activator.CreateInstance`. That only works if the assembly already sits in IntoChat's probing path, and it has no AssemblyLoadContext isolation. So every module is a ProjectReference in both IntoChat.csproj (runtime) and IntoChat.AppHost.csproj (hosting). A module's Aspire hosting defaults are linked by a string-typed `[ModuleHosting("Type, Assembly")]` attribute. Adding a capability therefore means editing AppHost.cs, AppHost.csproj and IntoChat.csproj, rebuilding, and restarting the silo.

### E2 (gap, high) [VERDICT: partially] ModuleDefinition has no manifest: identity is the CLR type name, with no version, description, permissions or pricing
`ModuleDefinition` holds three things: `ModuleType`, a configuration dictionary and dependencies. `Id` is `ModuleType.FullName`. `ModuleComposition.Resolve` already handles dependency order, cycles and conflicting configuration keys, and `CompositionOverrides` can carry validated option patches as a 32 KiB JSON envelope. Together these are a reasonable base for an install-time manifest resolver. Nothing records a semantic version, publisher, display name, purpose, required capabilities, permissions, tariffs, UI parts or data-retention policy. Composition happens only at AppHost level (cluster-wide), so there is no per-user or per-workspace enablement.

> CORRECTION: ModuleDefinition really does hold only ModuleType, Configuration and Dependencies, and Id is FullName (ModuleDefinition.cs:9-23). Two qualifications. (1) The 32 KiB CompositionOverrides envelope is a test-only channel: its key is "DigitalBrain:Testing:Overrides" (CompositionOverrideTransport.cs:9), and the only production reader applies it on the AppHost builder (DigitalBrainBuilder.cs:41-45), fed by E2ETest.cs:19. ### E5 (fact, high) [VERDICT: partially] code_contracts is the only catalog today: flat reflection over 4 hard-coded DLLs, no semantics, truncated at 24,000 characters
`ContractCatalog.Read` loads a hard-coded module map and reflects over exported types. The map is filled in CodingModule.PostConfigure with time, flutter, ai and google. It keeps INeuron interfaces, Signal records, IDigitalBrain and ISignalSubscription and renders them as 'FullName { Ret Method(Type p) }' strings. The JSON is capped at 24,000 characters by dropping contracts from the end; AI namespaces sort last, so they are dropped first. Allowed values, units, validation rules, examples, costs and descriptions are not included. The owner's failed card shows the effect: the catalog shows `Task Configure(String label, String kind)`, but the accepted kinds {text, number, password, suggest} live only inside TextFieldNeuron. The model chose "date" and the deploy failed. This is keyword-free, embedding-free listing, not search.

### E7 (fact, high) [VERDICT: partially] Memory module: one Qdrant collection, OpenAI 1,536-dimension embeddings, no product consumer, likely not durable

### E8 (gap, medium) [VERDICT: partially] No registry of neuron instances exists, so the assistant cannot 'remember neurons' today
Neuron identities are opaque derived strings: conversation-<sha256(scope, thread)>, behavior-<sha256(scope, id)>, "{scope}/apps/files/items". Orleans can list only currently active activations (`IManagementGrain.GetActiveGrains(GrainType)`), not persisted but inactive grains. Nothing records 'which neurons exist in my workspace, what they are, and when they were created'. The behavior catalog is the one exception: behavior descriptions are stored as local JSON documents (500 per workspace, single host). To make 'find my customers table' work, every neuron creation needs to be written to an explicit instance catalog (type, id, scope, title, created by, last used), which can then be embedded. Scanning grain storage is not a viable substitute.

### E10 (recommendation, medium) What indexing every part of the system would take
(1) Metadata: a CapabilityManifest per module, generated at build time by a source generator or at startup by reflection plus attributes. It should cover module id, version and purpose; neuron interfaces with methods and JSON-schema parameters including enums and allowed values (so 'date' fails at plan time, not deploy time); signals; UI kinds (29 in UIVocabulary) with their properties and events; agent tools (AIFunction.JsonSchema); cost tariffs. (2) Instance catalog (E8) plus behavior descriptions (BehaviorCatalogStore) and, later, app definitions. (3) Separate Qdrant collections for the system catalog (global, keyed by manifest hash), workspace instances (filtered by scope) and user memories, so switching embedding models or rebuilding the catalog never touches user notes. (4) Rebuild in the background, idempotently, with a keyword/BM25 fallback, following the E6 lessons. (5) Expose one `find_capability` or `search_system` tool, and let AgentTurnRunner attach the top-k matching tools dynamically instead of a hard-coded list (the ToolNames seam already exists). Size: about 55 neuron-interface files, about 85 signal records, 73 grain types, 29 UI kinds, about 20 tools, and at most 500 behaviors per workspace, so under 5,000 vectors, which is trivial for one Qdrant node. The hard parts are freshness, versioning, per-workspace scoping and authorization filtering (never embed secret values such as TextField passwords), not storage.

### E16 (recommendation, medium) Proposed app format: declarative apps for non-programmers, out-of-process code packages for developers
Tier 1, the default for non-programmers and the marketplace: a versioned JSON app definition as designed in intochat-neuron-app-composition.md. It covers Surface/Layout/Form composition, typed bindings to installed capabilities, required permissions and Compute budget. It is validated against the capability manifest (E10), installed per workspace at runtime, and needs no new code or silo restart. Tier 2, for developers: a signed package (NuGet plus manifest) whose code runs out of process, the way behaviors do via BehaviorApp (an Orleans client in its own process). It can be installed and uninstalled without restarting the silo and isolated with an OS or container sandbox and restricted credentials. Limitation: an out-of-process client can call neurons but cannot host grains. Third-party neurons would therefore need a platform-hosted proxy neuron, or a heterogeneous or rolling silo deployment for trusted first-party modules. 'LeadGenerator' fits Tier 1 plus existing capabilities (web lookup, the ClickHouse leads table). 'BackgroundRemover' is a Tier 2 capability exposed as a typed operation with a tariff. Reqnroll/BDD scenarios could be kept as the human-readable 'what this app does' text that gets indexed, but they were deleted before (E6), so reintroducing them is a product decision.

## Open questions
- Should third-party code ever run inside the silo with full trust, or must all marketplace code run out of process (behavior-style) or be declarative only?
- Is the first marketplace audience non-programmers (declarative app definitions over existing capabilities) or developers (signed code packages)? This decides whether Tier 1 or Tier 2 is built first.
- Should installs be per user, per workspace or per organization? Today composition is cluster-wide in the AppHost and scope is one BasicAuth username.
- The capability index was built and deleted twice (1 Aug Qdrant projection, 10 Aug in-process hybrid, 20 Aug full removal). What latency and failure budget is acceptable this time: non-blocking, keyword fallback, top-k tool attachment?
- Given the rule against boilerplate `/// <summary>`, which metadata source should feed semantic search: attributes on contracts, a per-module manifest file, or Reqnroll/BDD scenario text (removed before)?
- Should the assistant see only dynamically selected top-k tools found through search, replacing the hard-coded 16-tool list and monolithic prompt in ConversationCoordinator?
- Which installed-but-unreachable modules (ClickHouse, Memory, Salesforce, Gmail, GitHub, Aspire, Roslyn, DotNet, TestTwitter) stay in the product AppHost, and which get chat tools?
- Must vector memory survive AppHost restarts (add a Qdrant data volume or persistent lifetime)? Should system catalog, workspace instances and user memories live in separate collections?
- Is the Windows-only, host-privileged behavior worker acceptable for marketplace-distributed code, or is a cross-platform sandboxed executor a prerequisite?
- Who pays the Compute for index embeddings and discovery searches: the platform or the user?
