# H-projects-survey-bdd

## Summary
E:\intochat\Projects is not a product. It is an archive of seven or more earlier attempts at the same idea (ino, final, v3, v4, digitalbrain, self-improving, IAW), each started from scratch. Two design docs there matter for this question. The survey document concludes that no earlier attempt ever tested the full "signed typed-C# pack, installed into the running cluster, embodied, then dispatched" chain end to end. It says to use final's Reqnroll distribution feature (16 scenarios) as the test template. The distribution-algorithm pass says "reuse NeuroPack + .feature; do not invent a format". Both docs agree that Gherkin scenarios are the readable, executable description of software. They also agree that the payload is typed C#, never a DSL. Invariant #1 in CONTINUATION.md says the same.

The owner's idea has been built several times before, and each time it was deleted. Four earlier versions exist in the archive: .feature files embedded next to each neuron with a text search over them (old digitalbrain Introspector); scenarios tagged @neuron:<id> used as the assistant's routing list (ino); a feature-text spec run against a dynamic neuron (DynamicNeuronSpec + NeuronTestRunner); and a gate that runs a pack's own embedded test before activating it (v3 GateNeuron). The current repo also built and then removed three relevant pieces. (1) On 2026-08-01, commit ba26ac087 put modules, neurons, signals and behavior descriptions plus scenario titles into Qdrant, keyed by stable contract IDs. Its stated rule was that exact schema and version truth stays in a catalog. It was lost in the 2026-09-10 port; only an unused reserved-namespace guard remains. (2) On 2026-08-25, a Reqnroll behavior runtime was designed, using @behavior and @test scenarios, and activating only when compile and tests are green. It was replaced by typed C# behaviors. (3) On 2026-09-17, 26 .feature files were deleted, including describe.feature and clickhouse.feature. clickhouse.feature was a plain-English description of exactly the "show me all customers" flow the owner now finds hard to understand. Today the repo has zero .feature files and zero Reqnroll references.

Verdict: the idea is sound as a description and verification layer, and wrong as the program itself. What it enables is real. Scenarios are readable, executable specs. The pass/fail evidence from running them builds user trust. Their titles and examples are good search text for vector discovery and good few-shot examples for the model; Anthropic's docs say tool selection gets worse past 30–50 tools and support embedding-based tool search. They also make a regression suite for platform upgrades, the same idea as Pact contract testing. The current Coding module already seals artifacts with source, tests, a build-environment hash and a test report that must fully pass, so that is most of a certification format already. It is not readable by people and it accepts an artifact with zero author tests.

The costs are also real, and the repo's history shows them. The Gherkin/Reqnroll layer was deleted about five times as build overhead with no consumer. Non-programmers can agree on scenarios but cannot write the code behind each step. If an LLM writes both the code and the scenarios, the check proves nothing. Scenarios that call an LLM had to be mocked or marked @ignore in every earlier attempt.

The typed contract has to be the machine-readable truth. The "date" failure proves it. ITextField.Configure(string label, string kind) accepts any string, and the four allowed kinds sit in a private list inside the implementation. So the mistake only surfaced after deploy. An enum in the contract would have caught it at compile time. Nothing in the repo today lets the assistant read that contract: the MCP describe/call tools were deleted.

Recommended format: typed contracts (interfaces, signals, enums, versions) for machines. Declarative .feature scenarios bound to those contracts through a step library the platform owns, for people and for certification. A vector index over names, descriptions and scenario titles that returns contract IDs. A signed certification record (Cucumber Messages output, environment hash, publisher signature) stored with each marketplace listing.

### H8 (gap, high) The "date" failure comes from a stringly typed contract; scenarios alone would not have prevented it
ITextField.Configure(string label, string kind) accepts any string. The allowed kinds {text, number, password, suggest} live in a private HashSet inside TextFieldNeuron and throw ArgumentOutOfRangeException at runtime. So the LLM-authored behavior compiled, passed its checks, deployed, and then failed as a running behavior. An enum or value type in the contract would have failed in the Building stage and would be visible to the model. Scenarios add value on top: a readable example such as "Given a card with a date-of-birth field", and a regression check once date support ships. The type system is the first line of defence; BDD is the second.

### H11 (fact, high) Official docs: Reqnroll's HTML report and Cucumber Messages output replace the retired SpecFlow LivingDoc
Reqnroll formatters exist only in v3.0+. The HTML formatter produces a stand-alone file of executed features with results, "can also be used as a Living Documentation", and is the default replacement for SpecFlow+ LivingDoc; it cannot be customised yet. The Cucumber Messages formatter writes a standard .ndjson stream for other tools. Its message types include GherkinDocument, Pickle, StepDefinition, TestCase, TestStepFinished, Attachment and Meta, and Reqnroll 3.0+ emits them. SpecFlow reached end of life on 2024-12-31. LivingDoc was closed source, so Reqnroll could not fork it. Reqnroll turns .feature files into code-behind test classes at build time (Reqnroll.Tools.MsBuild.Generation). Embedding feature files as resources is opt-in (ReqnrollEmbedFeatureFiles). Consequence: a marketplace can store the Cucumber Messages output of an app's certification run as the evidence shown in its listing, with no report format to invent. Running scenarios inside a live, installable runtime needs either build-time generation in the sealed build or a runtime Gherkin parser plus binder (the 08-25 design).
Evidence: https://docs.reqnroll.net/latest/reporting/reqnroll-formatters.html; https://reqnroll.net/news/2025/06/roadmap-update-html-report/; https://reqnroll.net/news/2025/01/specflow-end-of-life-has-been-announced/; https://github.com/cucumber/messages; https://docs.reqnroll.net/latest/installation/configuring-build.html

### H12 (fact, high) Cucumber prior art: BDD's value is checked, shared understanding; imperative Gherkin is fragile
Cucumber describes BDD as three steps: Discovery, Formulation, Automation. Its key benefit is "producing system documentation that is automatically checked against the system's behaviour". Its guidance says scenarios should "describe what, not how"; imperative steps tied to the UI break whenever the implementation changes. The owner's own history drifted imperative and technical: ino's Given steps were regex alternations ("book a taxi|find a taxi|hail a taxi"), and the deleted IntoChat features used phrases like "'claude' waits up to 5 seconds until…". Neither is readable by a normal person in a marketplace listing.

### H13 (risk, medium) Authoring cost: non-programmers can agree on scenarios but cannot automate them, and LLM-written code plus LLM-written tests proves little
A regular person can approve or edit declarative Given/When/Then text (Cucumber's Formulation step). They cannot write the step code behind it (Automation). The 08-25 design handled this with a closed, platform-owned step catalog, editor completions, and "generated text is always compiled and tested before activation". If the assistant writes both the C# behavior and its scenarios in one pass (today's authoring loop writes draft.Source and draft.Tests together), verification is circular. Mitigation: the user approves the scenario text before code is generated; scenarios bind only to steps from the platform or the app's typed contracts; unknown steps fail closed, unlike the old NeuronTestRunner, which ignored them; and a separate step checks each scenario against the approved intent.

### H15 (recommendation, high) Discovery: index scenario titles and examples in vectors, return contract IDs, then load the typed definition
Anthropic's tool search docs say selection accuracy "degrades once you exceed 30–50 available tools" and that loading every tool up front can cost around 55k tokens. They support custom embedding-based search that returns tool_reference blocks, and discovered tools bring their input_examples along. A marketplace with many apps needs this. Declarative scenario titles ("Remove the background from a product photo") are good search text and ready-made few-shot examples. Use the ba26ac087 split: vectors return candidates (contract ID, artifact hash, visibility); the exact catalog is the truth for schema, version, permissions and tariffs. The owner's "memory of neurons" is the same index, filtered by the user's installed apps and live neuron instances.

### H16 (recommendation, medium) Re-certify installed apps on platform upgrades by re-running their scenarios, like Pact contract testing
Each sealed artifact already records a BuildEnvironment with hashes of every module assembly it compiled against. When the platform or a module changes, the platform can find affected installed apps (the hash differs) and re-run their scenarios on a staging silo before rollout. It can block the upgrade, or flag and pin the app to the previous deployment; BehaviorProgramNeuron already supports Rollback to a retained deployment. This is the Pact pattern: tests written from the consumer's side produce a contract that the provider checks before deploying. Here the installed apps' scenarios become the platform's regression suite. Open cost: re-certification uses compute per app per upgrade, which ties into the "Compute" currency. Someone has to pay for it.

### H17 (recommendation, medium) Proposed app description format: typed contracts, manifest, declarative features, signed evidence
Following the pass doc ("reuse NeuroPack + .feature, don't invent a format"), an app package would have four parts. (1) Contracts assembly: typed neuron interfaces and signals, using enums and value types instead of strings (see H8). This is the machine-readable truth for the compiler, the assistant and the approval UI. (2) Manifest: id, version, publisher, required permissions and secrets, per-operation tariffs in Compute, and approval requirements. (3) features/*.feature: declarative scenarios, each tagged with the contract it exercises (for example @neuron:<contractId>, like ino's tag) plus tags such as @charges or @requires-approval, with steps bound to platform steps or the app's typed contracts. (4) Certification evidence: the Cucumber Messages output from a sealed run on fakes, the BuildEnvironment hash, and the publisher signature (Ed25519 from final, or ECDSA plus licence from old digitalbrain). The feature titles and descriptions feed the vector index (H15). The listing page renders the features as living documentation with a pass badge (H11).

## Open questions
- Is Gherkin the app's program, or only its description and verification? The history suggests description plus verification, with typed C# as the program (CONTINUATION invariant #1, the 09-10 move to C# behaviors). Please confirm explicitly so the layer stops being added and deleted.
- For apps made by non-programmers, who writes the scenarios? Options: the user writes them from a closed step catalog; the assistant proposes them and the user approves the text before any code is generated; or both. Must scenario approval happen before code is written?
- Is a passing certification run on deterministic fakes required to list an app in the marketplace? What is the minimum, e.g. at least one author scenario per public contract operation, and should the Conformance-only loophole be closed?
- Are scenarios that depend on an LLM or external service allowed as hard gates, or only as scored evals shown on the listing (a quality number rather than pass/fail)?
- On a platform or module upgrade, do failing installed apps block the rollout, or are they flagged and pinned to their previous deployment? Who pays the Compute for re-certification: the platform, the publisher, or the user?
- Should the 2026-08-01 capability projection (modules, neurons, signals and behavior scenarios in Qdrant, returning contract IDs) be restored as the discovery layer, or redesigned around the new app manifest?
- Are an app's scenarios public on its listing? They document behavior, but they may reveal a publisher's business logic or data shapes.
- May marketplace apps bring their own neuron types (new grains, which needs the untested collectible-ALC embodiment chain), or only behaviors composed from installed contracts?
- Runtime mechanism: use Reqnroll's build-time code-behind inside the sealed build, a runtime Gherkin parser with the platform's own binder (the 08-25 design), or keep xUnit tests and render Gherkin-style documentation from them?
