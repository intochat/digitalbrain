# B-behaviors

## Summary
Behaviors are a C# code-deployment pipeline, not a way to build apps. Three modules take part. Coding holds drafts and checks: an LLM writes one C# file plus xUnit tests, and a pinned revision is compiled and tested in a contained process, then sealed as a SHA-256 artifact. Behavior holds the program: deploy, start, stop and rollback, with each run launched as its own Windows process that joins the silo as an Orleans client. IntoChat connects these to /agent through 14 tools, to the /author endpoint, to MCP and to a Flutter "Behaviors" manager. Separately there is an older in-process IBehavior host (ElonBitcoin, fed by a fake Twitter module wired into the product AppHost) and an orphaned ~2000-line Flutter "Programs" screen whose /programs backend returns 404. An author, or the LLM, has to track six identities (draft revision, check operation, artifact, program revision, deployment revision, generation) plus two state machines and readiness semantics.

Root cause of the date field failure, confirmed from the live draft and worker logs of behavior "person-card-form": the assistant wrote `dateOfBirth.Configure("Date of birth", "date")`. ITextField.Configure takes a plain `string kind`. The allowed values (text, number, password, suggest) exist only as a private HashSet inside the internal TextFieldNeuron. The contract catalog shows the model only `Configure(String label, String kind)`. So the model guessed an HTML-style "date" that no layer supports. Validation passed because it only compiles the code and runs the model's own tests; no real or test neurons are available during tests. The saved test was a tautology: it checks a constant defined inside the test file itself. The runtime then threw ArgumentOutOfRangeException ("(Parameter 'kind')", no allowed values listed) four times: the first run plus three retries. The program's error field says "Behavior control channel closed.", and the real exception appears only in logs that are mostly Orleans client startup messages.

Fixing "date" alone would not have helped. The card had no child references to the text fields. The neuron keys ("name", "surname", "person-card") are global rather than per-workspace. No workspace window was opened. The Flutter shell only knows how to render surfaces for the built-in Files and Image Editor apps. The renderer masks input only when kind == 'secret', which the server rejects, so a "password" field would show in clear text. The /agent assistant has no declarative UI tools at all. Any "draw me X" request is therefore pushed through C# code generation, compilation and deployment of a separate process. That path is the main source of the "a lot of trash" feeling, and it also makes Aspire traces noisy: the manager polls every 4 seconds, and each detail request produces about 21 spans.

The essential parts worth keeping for a marketplace are typed contracts, immutable verified artifacts, versions with rollback, clear lifecycle and readiness, and bounded logs. The accidental parts are stringly-typed parameters, LLM-written tests treated as proof, six identities and 14 tools exposed to the model, one OS process per one-shot job, duplicate authoring paths and host mechanisms, and polling. A simpler product model: an App = a manifest (identity, version, publisher, requested capabilities, tariffs) + typed inputs + a declarative UI surface checked against a schema generated from the UI vocabulary + optional handlers (on demand, on a signal, on a schedule), where a handler may be a verified C# artifact. Today's behavior pipeline becomes the "code handler" tier for developers, not the path for "draw a card". Before third-party apps can be distributed, the missing pieces are sandboxing (code currently runs as the host OS user with unrestricted access to every neuron), per-neuron permissions, per-workspace scoping, install/uninstall, and metering hooks for Compute.

### B2 (gap, high) [VERDICT: confirmed] The contract hides the allowed field kinds, so the model had to guess
ITextField.Configure(string label, string kind) is the whole public contract. The allowed values are a private static HashSet inside the internal grain class. ContractCatalog shows the LLM each method as 'Task Configure(String label, String kind)', with no enum values, no defaults and no docs. An LLM that knows HTML input types will naturally try 'date'. The exception message ('Specified argument was out of the range of valid values. (Parameter 'kind')') does not list the valid values either, so the model cannot fix itself from the error. Supported kinds today: text (default), number, password, suggest (case-insensitive). No date, email, multiline, select or checkbox kind exists (toggle and slider are separate neurons).

### B7 (fact, high) [VERDICT: partially] Lifecycle and concepts a behavior author must know today
Draft: ICodeDraft with Revision, Source, Tests, ModuleIds and LatestCheckId; saves use optimistic concurrency with ExpectedRevision and a fresh OperationId. Check statuses: Queued, Building, Testing, then Passed, Failed, Cancelled or Interrupted; only Passed carries a CodeArtifactRef. Program commands (IBehaviorProgram): Deploy(artifact, config JSON limited to Behavior__* keys, 32 KiB, no secrets), Start, Stop, Rollback(deployment revision). DesiredState is Stopped or Running. ExecutionState is Stopped, Starting, Running, Stopping, Completed, Failed or Interrupted. Ready becomes true only after every declared SubscriptionRequirement is established. Failure retries up to 3 times with 1/2/4 s backoff. Host restart marks active runs Interrupted. There is no Delete, Disable or Uninstall: Stop is the only 'disable', and the workspace catalog (500-item cap) cannot shrink. Six separate identities are exposed: draft revision, check operation, artifact ID, program revision, deployment revision and generation. The SDK has BehaviorApp.RunAsync<T>, IBehavior.RunAsync, SubscriptionRequirement.For<TSignal>, and two listening APIs (SubscribeAsync+ReadAllAsync, and the brain.On<T> extension). The Flutter UI hard-codes enum orders as integer indexes.

### B13 (risk, high) [VERDICT: confirmed] The trust model does not fit a marketplace: generated code runs as the host OS user with unrestricted access to every neuron
The README says process containment is 'not a hostile-code sandbox'; generated code and tests run with the host OS user's privileges. ### B17 (recommendation, medium) Essential vs accidental complexity in the behavior model
ESSENTIAL (keep and promote to marketplace primitives): typed neuron contracts as the only integration surface; immutable, content-addressed verified artifacts (SHA-256 over source, tests, environment and payload); versions with rollback; desired vs actual state with honest readiness; bounded and quota'd storage and logs; process isolation boundary; audit of who deployed what (AgentRunId). ACCIDENTAL (remove or hide): stringly-typed parameters; LLM-written tests counted as verification; six identities and CAS/UUID ceremony in tool arguments; 14 LLM tools plus a separate /author path plus MCP duplicates; one OS process plus Orleans client for every one-shot job; file-JSON stores with 100 ms polling; the in-process ElonBitcoin host and TestTwitterModule in product; the orphaned Programs UI; duplicate process runners; UI polling instead of existing signals; free-text 'declared triggers/effects' (behavior_describe) that the code never enforces.

### B18 (recommendation, medium) Simpler product model: App = manifest + typed inputs + declarative UI + optional handlers; C# behaviors become the developer tier
Tier 1, declarative UI/forms (non-programmers, 'draw a card'): the assistant produces a JSON surface definition validated against a schema generated from UIVocabulary (enum kinds including date). It renders at once with no compile step. Values are typed (Text, Number, Date, Secret) and bound to neurons in the app's scope. Tier 2, automations: trigger (signal, schedule or on-demand command) → action on a typed neuron operation with typed inputs, validated against contract schemas before activation. Tier 3, code handlers (developers): today's draft → check → artifact → program pipeline, invoked by Tier 1/2 manifests. The LLM would see 3–4 coarse tools (app_define, app_validate, app_install/run, app_status) with server-managed revisions. Each app gets a workspace-scoped key prefix and a surface opened in a workspace window, so what the user asked for becomes what they see.

### B19 (recommendation, medium) How behaviors map to marketplace apps, and what is missing
Reusable: sealed artifacts serve as release versions, deployment revisions and rollback serve as app updates, DesiredState serves as enable/disable, readiness serves as health, and bounded logs serve as support diagnostics. Missing for a marketplace: (1) a package/manifest format with publisher, version, description, requested neuron capabilities, input schema, UI entry surface and Compute tariffs; (2) install, uninstall and delete (IBehaviorProgram has no Delete, and the catalog has no removal); (3) per-user or per-workspace instances rather than global keys; (4) a sandboxed executor backend plus a capability-checked brain proxy for untrusted publishers; (5) metering hooks per LLM token, grain call and storage byte, with approval gates before paid runs and retries; (6) discoverability: manifests, contracts and descriptions indexed in the Memory/Qdrant module so the assistant can find 'BackgroundRemover' by intent; (7) contract-level validation (schema + simulated neurons), so 'validated' in the store means 'will run'.

## Missed (from verifier)
- Every Orleans grain call is traced twice across the whole system, which is a large share of the Aspire trace noise. The live exception stack in the silo shows two Orleans.Runtime.ActivityPropagationGrainCallFilter.Process frames in the incoming pipeline (log entry seq 15 of person-card-form). Every grain call appears as Client→Client→{Server,Server} (traces 45951532bd1605a3ade04c19f7a739b5, c1f591f73d106341723137c766b3e5f4). The explicit registration is silo.AddActivityPropagation() at src/Modules/DigitalBrain/Kernel/Aspire/DigitalBrainRuntimeHostingExtensions.cs:40. The second registration is unconfirmed, possibly EnableDistributedTracing config supplied through the Aspire Orleans integration (https://learn.microsoft.com/dotnet/orleans/host/monitoring/#distributed-tracing notes either the API or the EnableDistributedTracing option enables it). Fixing it would roughly halve grain spans.
- The shell always runs an InboxBanner that polls every 2 s: GET /ui/inbox plus 5 hard-coded 'e2e' demo neurons (charts, browsers, videos, expanders, buttons). Evidence: src/Modules/Google/Flutter/app/shell/lib/inbox_banner.dart:17,30,41-76; mounted at workspace_app.dart:1346 whenever programmingClient != null. Aspire shows GET /ui/charts/e2e every ~2 s, 5 spans each. That is about 6 requests and about 28 spans every 2 s regardless of user activity. It is a second demo artifact in the product shell, alongside ElonBitcoin/TestTwitterModule.
- An unscoped UI-kit HTTP surface exists: GET /ui/{collection}/{name} for every UI neuron (src/Modules/Google/Flutter/Flutter/Shared/UiHttp.cs:12; UiKitEndpoints.cs:37-82), with POST routes including textfield Configure/SetValue (UiKitEndpoints.cs:77,82). Any client can read TextFieldState.Value, including a 'password' kind, or reconfigure any UI neuron by global name with no workspace check. That contrasts with the scoped /workspaces/{id}/apps/node route (AppEndpoints.cs:70). This matters for the owner's 'store my password' question and for marketplace isolation.
- Host activation policy can be bypassed from inside a behavior. AllowActivation is checked only in ScopedBehaviorTools and BehaviorAuthoringService (src/Applications/IntoChat/IntoChat/Behavior/BehaviorToolService.cs:26,69-75), not in BehaviorProgramNeuron (src/Modules/DigitalBrain/Behaviors/Behavior/Programs/BehaviorProgramNeuron.cs:17-45). Worker code has a full Orleans client, so it can Deploy/Start any program or call IAgent (LLM spend) with no metering. That is directly relevant to 'Compute' billing and to marketplace consent.
- A declarative UI composition seam already exists and was not mentioned. AppSurfaceComposer builds Surface → Layout → UiChildRef trees server-side for the Files and Image Editor apps (src/Applications/IntoChat/IntoChat/Apps/AppSurfaceComposer.cs:15-67), and the shell renders them. A 'create form/card' tool that composes these neurons under <scope>/apps/... is the natural simplification. It would avoid C#, compilation, a worker process and the global-key problem for 'draw me a card' requests.
- There is no user-input date primitive in the UI kit, although a validated date text input exists elsewhere. ICalendar is display-only (Set(mode, selected)/Read, no selection event; src/Modules/Google/Flutter/Contracts/Calendar/ICalendar.cs:9-10). /apps/event accepts only button/textfield/tabs/collection (AppEndpoints.cs ~91-100). Meanwhile the data-table filter already implements a YYYY-MM-DD date input with TextInputType.datetime and validation (src/Modules/Google/Flutter/app/ui/lib/src/components/table/ui_data_table.dart:444-452,536-541). That pattern could back a 'date' textfield kind.
- Worker logs are stored as raw 4096-char stdout/stderr chunks, not log records (LocalBehaviorExecutor.cs:133-138). One 'entry' can hold several log lines, for example the 1.6 KB ClientOptionsLogger dump at seq 10. The 10,000-entry retention limit is therefore not a line budget, and structured severity filtering is impossible. The worker also runs in 'Hosting environment: Production' with default Information logging, which produces the chatter.
- The /author endpoint loads the full catalog with modules=[] (catalog.Read([]), which calls Assembly.LoadFrom on every host DLL) and embeds it serialized into the agent instructions on every call (src/Applications/IntoChat/IntoChat/Behavior/BehaviorAuthoringService.cs:26,35). No Dart client references it (grep of the Flutter app finds no '/author'), so it is an API/test-only third authoring path with its own prompt and no activation-state wait.

## Open questions
- Should requests like 'draw me a card/form' be served by a declarative UI definition (no code, instant render) instead of generating, compiling and deploying C#? That decides whether the /agent assistant gets UI composition tools.
- Is the marketplace aimed at untrusted third-party publishers from day one, which requires a sandboxed executor backend (containers/WASM/remote) and capability-scoped neuron access? Or only curated, trusted publishers first, where today's local Windows-process model could be tolerated?
- What is the unit a marketplace sells and installs: an app definition (manifest + UI + handlers) instantiated per workspace, or a single running behavior? And should C# behaviors be visible to non-programmer users at all, or only to developers?
- Which typed input kinds are in scope for v1 (date, email, multiline, select, checkbox, file, secret)? Should secret/password values ever be stored in grain state, or only in a secrets store referenced by handle?
- Should failed runs retry automatically when they consume Compute (LLM tokens, paid app calls)? Who is charged for retries and failed validation builds, and do retries need user approval?
- May the orphaned or demo mechanisms be deleted: the Flutter WorkspacePrograms screen (/programs 404), in-process ElonBitcoin + TestTwitterModule in the product AppHost, Compile-Removed HTTP files, and the duplicate /author path?
- Should apps and behaviors have a real 'uninstall/delete' (removing the catalog entry, retained artifacts and logs), and what retention does rollback history need?
