# K-typed-data-agent-os

## Summary
IntoChat has no shared type system for values. Each layer keeps its own string vocabulary: the UI TextField accepts only {text, number, password, suggest}; Supabase and ClickHouse each keep their own text/number/date/boolean maps; the Flutter client uses bare strings. The owner's failed "card with a date-of-birth field" happened because of this: TextFieldNeuron rejects the kind "date" at runtime, even though the UI kit already ships a Calendar widget and both data modules already validate ISO dates. Sensitive values are handled worse. A "password" TextField is saved in plain text in grain state, broadcast in a change signal, and returned by GET /apps/node. The Flutter client masks the input only when kind == 'secret', a kind the backend never accepts, so passwords appear in clear text. Salesforce and Gmail OAuth access and refresh tokens are plain strings in grain state stored in Azure Blob. In dev runs, GenAI traces capture full message content by default. The repo has no data classification or redaction anywhere.

The major platforms have settled on the same answer, with 4 parts:
1. **A small closed set of typed value kinds.** Apple App Intents parameter types; Windows App Actions entity kinds (Text, File, Photo, Document, Table, Contact); MCP elicitation's flat primitives with the formats email, uri, date and date-time; Dataverse, Airtable and Notion field types.
2. **Addressable entities with stable IDs, resolved lazily.** Apple AppEntity and EntityQuery ("What is the entity for this ID?"), IndexedEntity for the semantic index, and WWDC26 EntityCollection, which passes only IDs.
3. **A semantic type is a primitive plus a format.** The format drives both validation and the choice of widget. Dataverse says formats "instruct the UI about which control to use". Power Pages maps Date only → Date picker and Currency → Currency input.
4. **Secrets never enter the model's context.** MCP says servers MUST NOT use form elicitation for passwords, API keys or tokens, and must use URL mode instead. The OpenAI Apps SDK sends `_meta` to the UI but never to the model. The same idea appears in 1Password Secure Agentic Autofill, `op://` references, Auth0 Token Vault, Key Vault references and JSON Schema `writeOnly`.

Recommended shape for IntoChat. A semantic type catalog where each entry has:
- a primitive
- a format and validation rules, written as JSON Schema keywords
- a sensitivity class: Public, Personal, SpecialCategory, Financial, Credential
- how much the LLM may see: the value, a masked value, or only a reference
- an input widget and a display widget
- a redactor

The catalog is published as JSON Schema with `x-intochat-*` extensions, so the same definitions work with MCP elicitation, OpenAPI and the Apps SDK without translation.

Values live in 2 places:
- **An owner Personal Data Vault.** Typed fields such as me.birthDate or me.email. Every access is decided per (app, semantic type, mode) and can be revoked. The vault supports GDPR export and erasure and keeps an audit trail.
- **App-private state inside each app's neurons.** It holds references to vault items, and copies only under a grant.

Values become first-class addressable objects in the AppEntity sense: they get a stable ID and can be referenced across apps. They do not each need their own grain. A value is not a new grain per value by default.

Consent follows the HealthKit and Solid WAC model: per type and per direction (read, write, append). If access is denied, the app cannot tell a denied value from an empty one. Anything with side effects goes through preview → confirm, which generalizes the existing Salesforce PrepareWrite/ConfirmWrite.

The assistant handles secrets only by reference. It sees a handle and a label, never the value. The value is resolved inside the neuron or HTTP call that performs the effect. Secrets are entered through an out-of-band UI or URL channel, never typed into chat. OAuth tokens move to a Token Vault neuron. Secret values are kept out of signals, traces, Qdrant memory and journals. At rest they are encrypted through the existing IGrainStorageSerializer seam.

Some pieces for this already exist in the repo but stand alone or are unfinished:
- TokenHandoff: a one-use nonce that passes OAuth tokens by reference
- Salesforce preview/confirm writes
- Memory's ProtectedPayloadReference: a reference type that nothing ever resolves
- a system-prompt rule saying "Never request database credentials in chat"

The work is to promote these into platform-level types, not to invent new mechanisms.

## Findings

### K1 (fact, high) Value types are fragmented string vocabularies; 'date' is rejected by the UI TextField, which is exactly why the owner's DOB card failed
There is no shared type catalog. TextFieldNeuron hard-codes Kinds = {text, number, password, suggest} and throws ArgumentOutOfRangeException for anything else, so an agent-authored behavior that configures a 'date' field fails at deploy or run time. This matches the owner's 'runtime rejected the date field kind "date"' error. Other type vocabularies exist in parallel: Supabase (text/number/date/boolean, internal static class), ClickHouse (its own constants and date validation yyyy-MM-dd), the Flutter TableColumn.type string, and the UI Table's TableColumn, which has no type at all. The UI kit already ships a Calendar widget neuron, but nothing links a 'date' value to it.
Evidence: src/Modules/Google/Flutter/Flutter/TextField/TextFieldNeuron.cs:15 (Kinds = text, number, password, suggest); src/Modules/Google/Flutter/Flutter/TextField/TextFieldNeuron.cs:21 (throws on unknown kind); src/Modules/Supabase/Supabase/Query/SupabaseTypeMap.cs:5-17; src/Modules/Supabase/Supabase/Table/SupabaseTablePolicy.cs:25-26 ('Column type must be text, number, date or boolean'); src/Modules/ClickHouse/ClickHouse/ClickHouseTypeMap.cs:10; src/Modules/ClickHouse/ClickHouse/Tables/ClickHouseTablePolicy.cs:85; src/Modules/Google/Flutter/app/core/lib/src/models/table_models.dart:2-22; src/Modules/Google/Flutter/Contracts/Table/ITable.cs:15 (TableColumn(Id, Title) - untyped); src/Modules/Google/Flutter/Contracts/Calendar (Calendar widget neuron exists)

### K2 (risk, high) 'password' fields are stored in plaintext, broadcast in signals, returned over HTTP, and rendered unmasked (backend 'password' vs client 'secret' mismatch)
The backend accepts kind 'password'. The Flutter renderer sets obscureText only when definition['kind'] == 'secret', a kind the backend rejects, so a password field is displayed in clear text. SetValue stores the raw value in TextFieldState.Value, persists it through the default grain storage, and publishes TextFieldChanged(Name, Value) to every observer. GET /workspaces/{id}/apps/node?kind=textfield returns the whole state, value included. This is the concrete case of the owner's question 'if the system stores my password and later uses it, how does that work?': today it does not, safely.
Evidence: src/Modules/Google/Flutter/Flutter/TextField/TextFieldNeuron.cs:15,30-37; src/Modules/Google/Flutter/Contracts/TextField/ITextField.cs:20-21 (Kind, Value as plain strings); src/Modules/Google/Flutter/Contracts/TextField/Signals/TextFieldChanged.cs:6 (signal carries Value); src/Modules/Google/Flutter/app/ui/lib/src/composition/neuron_view.dart:184 (obscureText: kind == 'secret'); src/Applications/IntoChat/IntoChat/Apps/AppEndpoints.cs:75 (GET returns ITextField.Read()); src/Applications/IntoChat/IntoChat/Apps/AppEndpoints.cs:92 (POST SetValue)

### K3 (risk, high) OAuth access and refresh tokens are plain fields in grain state persisted to Azure Blob; there is no vault and no field-level encryption
SalesforceState and GmailState keep AccessToken and RefreshToken as string properties. SalesforceNeuron persists them with [PersistentState("state", DefaultGrainStorage)], which goes to the blob container 'digitalbrain-v2-state' through the plain Orleans binary serializer. Each module re-implements refresh (SalesforceTokenRefresh, GmailTokenRefresh), so every marketplace app would repeat this pattern. The runtime already registers a custom keyed IGrainStorageSerializer, which gives an existing seam for an encrypting serializer. Orleans documents GrainStorageSerializer as configurable per provider.
Evidence: src/Modules/Salesforce/Salesforce/Salesforce/SalesforceState.cs:5-6; src/Modules/Salesforce/Salesforce/Salesforce/SalesforceNeuron.cs:19; src/Modules/Google/Gmail/Gmail/Gmail/GmailState.cs:7-8; src/Modules/DigitalBrain/Kernel/Aspire/DigitalBrainRuntimeHostingExtensions.cs:33-38 (custom IGrainStorageSerializer + container name); src/Modules/Salesforce/Salesforce/Salesforce/SalesforceTokenRefresh.cs:7-22; src/Modules/Google/Gmail/Gmail/Gmail/GmailTokenRefresh.cs:7-27; https://learn.microsoft.com/dotnet/orleans/host/configuration-guide/serialization#grain-storage-serializers

### K4 (risk, high) Dev traces capture full LLM message content by default, and there is no data classification or redaction anywhere in the codebase
The AppHost sets AI Telemetry.EnableSensitiveData = true whenever Environment=Development and it is in run mode, and AIOptions also honours OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT. Any DOB, password or customer row that reaches the model therefore lands in Aspire traces. This is part of the owner's 'too much trash in traces', and also a PII leak. A repo-wide grep for DataClassification, Microsoft.Extensions.Compliance, redact or PII finds only ad-hoc string replacement (the Tavily API key, BrowserLoginSurface). .NET provides DataClassification plus redactors (ErasingRedactor, HmacRedactor) wired into logging through EnableRedaction, and this pairs naturally with a sensitivity class on each semantic type.
Evidence: src/Applications/IntoChat/AppHost/AppHost.cs:35-42; src/Modules/AI/AI/Configuration/AIOptions.cs:55-56; src/Modules/AI/AI/WebSearch/TavilyWebSearch.cs:59 (only ad-hoc redaction); https://learn.microsoft.com/dotnet/core/extensions/compliance; https://learn.microsoft.com/dotnet/core/extensions/data-redaction; https://learn.microsoft.com/dotnet/core/extensions/logging/source-generation#redacting-sensitive-information-in-logs

### K5 (pattern, high) Several pieces of a safe design already exist in the repo but are local or unfinished (handoff nonce, preview/confirm, dangling payload reference, prompt-only secret rule)
(a) TokenHandoff passes OAuth tokens by a one-use, 32-byte random nonce that expires in 2 minutes. That is reference-not-value, but it lives in memory and applies only to login. (b) Salesforce exposes PrepareWrite then ConfirmWrite ('Submits the confirmed write preview once'), a preview-then-approve pattern for side effects. (c) Memory defines ProtectedPayloadReference (a Guid plus an expiry), but no store or resolver exists anywhere in src. It is a reference type with nothing behind it. (d) The system prompt says 'Never request database credentials in chat; the connection string is configured through Aspire', so the secret policy is enforced by prompt text, not by types. These should become platform-level SDK types: SecretRef, a Grant, and Preview/Confirm.
Evidence: src/Modules/DigitalBrain/Kernel/Sdk/Auth/TokenHandoff.cs:6-50; src/Modules/Salesforce/Contracts/Salesforce/ISalesforce.cs:17-21; src/Modules/Memory/Contracts/Memory/ProtectedPayloadReference.cs:1-22; src/Modules/Memory/Memory/Memory/Qdrant/QdrantVectorMemoryProvider.cs:365-380 (only reads/writes the id); src/Modules/AI/AI/ConversationalAgent.cs:74-76

### K6 (gap, high) The vector memory (Qdrant) stores raw text with no sensitivity tagging, so a 'find anything via vector DB' plan would index PII and secrets
Remember(Namespace, Key, Text, Tags, Payload) upserts Text verbatim into the Qdrant point payload next to the embedding. Tags are free-form name/value pairs with no classification. If the owner's plan to index all neurons and namespaces in the vector DB includes value-bearing neurons (such as TextFields holding passwords or DOBs), secrets and personal data become retrievable by semantic search and can be returned into LLM context. Apple takes the opposite approach: IndexedEntity indexes only the properties the developer tags with indexingKey.
Evidence: src/Modules/Memory/Contracts/Memory/Remember.cs:6-11; src/Modules/Memory/Contracts/Memory/MemoryTag.cs; src/Modules/Memory/Memory/Memory/Qdrant/QdrantVectorMemoryProvider.cs:40-75 (TextField = text); https://developer.apple.com/videos/play/wwdc2025/244/ (IndexedEntity, @Property(indexingKey:))

### K7 (pattern, high) Apple App Intents: a closed set of typed parameters plus addressable AppEntity with a persistent ID, a display representation and a query; metadata is extracted at build time
Parameters may be Bool, Int, Double, String, Duration, Date, Decimal, Measurement, URL, IntentPerson, IntentFile, arrays of these, or any AppEntity or AppEnum. An AppEntity requires a persistent ID ('the system may save it in a shortcut'), a displayRepresentation and a defaultQuery. 'All queries must answer one very specific question, What is the entity for this ID?' so the system references entities by ID and resolves them only when needed. AppEnum is for constant sets and AppEntity for dynamic data. 'Your Swift source code will be read at build time to generate its App Intents representation … the system will use this data to understand your app's capabilities without needing to run your app.' WWDC26 added EntityCollection, which passes only identifiers ('almost instant' for 1000 photos), ValueRepresentation for sharing system-understood structured types across apps, and native PersonNameComponents and Duration. Lesson for IntoChat: values that cross app boundaries should be addressable entities (stable ID plus display label plus resolver), and the catalog should be discoverable without activating grains.
Evidence: https://developer.apple.com/documentation/appintents/appentity; https://developer.apple.com/videos/play/wwdc2025/244/; https://developer.apple.com/videos/play/wwdc2026/345/; https://developer.apple.com/videos/play/wwdc2024/10134/

### K8 (pattern, high) Apple App Schemas: shared per-domain typed contracts the assistant already understands, validated at build time
'App schemas give Siri a predefined understanding of common concepts, like messages, contacts, or documents.' Apps conform entities with @AppEntity(schema: .messages.message). 'Apple Intelligence only uses the properties that each schema defines.' 'If your type is missing a required property, Xcode generates an error at build time with a Fix-It.' Implication: IntoChat's semantic types such as Person, Date or Email should be one platform vocabulary that every marketplace app conforms to, not per-app strings. Conformance should be checked when the app or behavior is compiled (Roslyn and the behavior pipeline already run verification) so a 'date' mismatch fails at authoring time with a fix, not at runtime.
Evidence: https://developer.apple.com/videos/play/wwdc2026/240/; https://developer.apple.com/documentation/appintents/making-actions-and-content-discoverable-by-apple-intelligence; src/Modules/DigitalBrain/Behaviors/Behavior/Programs/BehaviorProgramNeuron.cs:18-25 (deploy verifies artifact, not value types)

### K9 (pattern, high) Windows App Actions and MCP on Windows: a small closed entity-kind enum, a JSON action manifest, per-invoker allow-lists, and contained connectors with identity and audit
The action definition JSON declares inputs and outputs by ActionEntityKind, a case-sensitive closed set: File, Photo, Document, Text, StreamingText, RemoteFile, Table, Contact. The Contact entity carries Email, FullName, Title and Description. Actions also declare allowedAppInvokers, usesGenerativeAI, displaysUI, contentAgeRating, inputCombinations with descriptions, and 'where' predicates. The Windows On-device Agent Registry puts MCP connectors 'in a separate environment … can only access approved resources', lets users and admins control access per agent, and logs interactions. Lesson: a marketplace app manifest should declare typed inputs and outputs from the shared catalog, who may invoke it, and whether it uses GenAI (relevant to Compute billing).
Evidence: https://learn.microsoft.com/en-us/windows/ai/app-actions/actions-json; https://learn.microsoft.com/en-us/windows/ai/mcp/overview

### K10 (pattern, high) Android AppFunctions and Credential Manager: annotated typed functions indexed by the OS, callers gated by permission; credentials come from providers after user selection
AppFunctions 'empowers your apps to behave like on device MCP servers'. Functions use @AppFunction(isDescribedByKDoc = true), and their parameter and return types use @AppFunctionSerializable. 'The AppFunctions Jetpack library generates an XML schema file … The Android OS uses this file to index the available AppFunctions.' 'Callers must have the EXECUTE_APP_FUNCTIONS permission to discover and execute AppFunctions.' Credential Manager unifies passkeys, passwords, federated sign-in and digital credentials, served by credential providers (password managers) through a system bottom sheet where the user picks a credential. The app never browses the credential store. Lesson: typed function schemas generated from code plus a caller permission; credentials flow from a trusted provider on user selection.
Evidence: https://developer.android.com/ai/appfunctions; https://developer.android.com/identity/credential-manager

### K11 (pattern, high) MCP elicitation already defines the minimal typed-input catalog and the secret rule IntoChat needs: flat primitives plus formats, and never secrets through the client
Form-mode requestedSchema is 'limited to flat objects with primitive properties only': string (minLength, maxLength, pattern, format ∈ {email, uri, date, date-time}), number or integer (minimum, maximum), boolean, and single or multi-select enum with titles. Clients use it to 'Generate appropriate input forms, Validate user input'. 'Servers MUST NOT use form mode elicitation to request sensitive information such as passwords, API keys, access tokens, or payment credentials' and 'MUST use URL mode' so that 'sensitive credentials never pass through the LLM context, MCP client or any intermediate MCP servers'. Responses are accept, decline or cancel. The owner's 'card with name, surname and date of birth' request is exactly a form-mode elicitation. Adopting this schema subset as the base layer of the catalog makes IntoChat forms interoperable with MCP servers from the marketplace.
Evidence: https://modelcontextprotocol.io/specification/2025-11-25/client/elicitation

### K12 (pattern, high) OpenAI Apps SDK: a two-channel tool result (model-visible structuredContent vs UI-only _meta), required behavior annotations, and 'no secrets in component props'
'Only structuredContent and content appear in the conversation transcript. The host forwards _meta to the component so you can hydrate UI without exposing the data to the model.' Tool descriptors require readOnlyHint, destructiveHint ('so the host knows to elicit explicit approval first') and openWorldHint. The security guidance says 'Include only the data required for the current prompt. Avoid embedding secrets or tokens in component props', 'Redact PII before writing to logs', and requires human confirmation for irreversible operations. Lesson: IntoChat tool and neuron results should split into a model channel (references and masked values) and a UI channel (real values rendered by trusted widgets). This fits the existing pattern where show_supabase_query_table opens a live table in the workspace.
Evidence: https://developers.openai.com/apps-sdk/reference; https://developers.openai.com/apps-sdk/guides/security-privacy; https://developers.openai.com/apps-sdk/app-submission-guidelines; src/Applications/IntoChat/IntoChat/Agent/SupabaseWorkspaceTools.cs:16-29

### K13 (pattern, high) JSON Schema and OpenAPI provide the wire vocabulary: format keywords, writeOnly for passwords, content media types, and x- extensions
JSON Schema 2020-12 defines the formats date-time, date, time, duration, email, idn-email, hostname, ipv4, ipv6, uri, uri-reference, iri, uuid, uri-template, json-pointer and regex. Format is an annotation by default; assertion requires the format-assertion vocabulary, so the runtime must validate explicitly. writeOnly means 'the value is never present when the instance is retrieved from the owning authority … writeOnly would be used to mark a password input field.' contentEncoding and contentMediaType describe binary files and images. OpenAPI adds format: password, 'A hint to UIs to obscure input', and allows x- specification extensions. Lesson: the catalog can be expressed as JSON Schema plus x-intochat-sensitivity, x-intochat-widget and x-intochat-llm-exposure, and every Secret field is writeOnly.
Evidence: https://json-schema.org/draft/2020-12/json-schema-validation; https://spec.openapis.org/oas/v3.1.0.html

### K14 (pattern, high) Dataverse, Power Apps, Airtable and Notion: a semantic type is a primitive plus a format, the format picks the control, and sensitivity is per column with masking
Dataverse Email and Phone are StringType with a format. 'Date Only' is DateTimeType with DateOnly behavior: 'Use this for data like birthdays and anniversaries.' Currency is MoneyType, and File and Image are separate types. 'The format … instruct[s] the UI about which control to use for that type.' Power Pages maps types to components: Date only → Date picker, Currency → Currency input, Email → Text box with email format, Choice → Dropdown, Yes/No → Toggle, File → File upload. Column-level security grants Read, Read unmasked, Update and Create per column, with masking rules. 'The calling application can't distinguish between a value that is secured and a value that is null.' Airtable's 28 field types and Notion's ~21 property types converge on the same set: text, long text, number, currency or percent formats, date, email, phone, URL, single or multi select, checkbox, attachment or files, user or people, linked record or relation, plus computed and system fields. This is strong evidence for a catalog of about 20 semantic types, not an open-ended one.
Evidence: https://learn.microsoft.com/power-apps/maker/data-platform/types-of-fields; https://learn.microsoft.com/power-apps/maker/data-platform/create-edit-field-solution-explorer#column-data-types; https://learn.microsoft.com/power-apps/developer/data-platform/data-type-format-conversions#supported-formats-by-data-type; https://learn.microsoft.com/power-pages/getting-started/add-form#dataverse-data-type-support-for-genai-forms; https://learn.microsoft.com/power-apps/developer/data-platform/column-level-security#display-masked-data; https://learn.microsoft.com/power-platform/admin/field-level-security; https://support.airtable.com/docs/supported-field-types-in-airtable-overview; https://developers.notion.com/reference/property-object

### K15 (pattern, high) Composite personal types (Person, PostalAddress, labeled contact points) are standardized by schema.org and Apple Contacts, including partial and limited access
schema.org Person has birthDate: Date, email: Text, telephone: Text, address: PostalAddress|Text, givenName and familyName, and identifier. PostalAddress has streetAddress, addressLocality, addressRegion, postalCode, addressCountry (ISO 3166-1 alpha-2 recommended) and postOfficeBoxNumber. Apple CNContact is immutable, thread-safe and ID-addressable, with birthday as DateComponents, phoneNumbers as [CNLabeledValue<CNPhoneNumber>] and postalAddresses as [CNLabeledValue<CNPostalAddress>]. Apps fetch only the keys they need (keysToFetch), and CNAuthorizationStatus includes 'limited: a limited subset of contacts, chosen by the person'. Lesson: IntoChat's Person type should reuse schema.org names, support labeled multi-values (work or home email), and support partial projection per grant. Today the UI PersonState is only DisplayName and AvatarUrl.
Evidence: https://schema.org/Person; https://schema.org/PostalAddress; https://developer.apple.com/documentation/contacts/cncontact; https://developer.apple.com/documentation/contacts/cnauthorizationstatus; src/Modules/Google/Flutter/Contracts/Person/IPerson.cs:9-20

### K16 (pattern, high) HealthKit: consent per data type and per direction (read vs share), lazy requests, and denial that apps cannot distinguish; DOB is a separate read-only characteristic
'You need to request permission to both read and share each data type.' 'People can also toggle individual read and share permissions within each category' and change them at any time. 'HealthKit intentionally prevents your app from distinguishing between full access and denied access to specific types.' Apple advises waiting 'until you need to access the data before asking for permission.' dateOfBirth, biologicalSex and bloodType are characteristic types, a separate category from samples. Lesson: grants in IntoChat should be keyed by (app, semantic type, mode) and requested just in time. A denied read should look the same as 'no value', so a marketplace app cannot probe what the owner has.
Evidence: https://developer.apple.com/documentation/healthkit/authorizing-access-to-health-data; https://developer.apple.com/documentation/healthkit/hkcharacteristictypeidentifier

### K17 (pattern, high) Secrets for agents are handled by reference and resolved at the effect boundary: op:// references, Key Vault references, 1Password agentic autofill, Auth0 Token Vault
1Password secret references op://<vault>/<item>/[section/]<field> 'remove the risk of exposing plaintext secrets' and always resolve to the latest value. Azure Key Vault references @Microsoft.KeyVault(SecretUri=…) are resolved by the platform with 'no code changes'. If a reference fails to resolve, the reference string is used instead, so the reference itself is never a secret. 1Password Secure Agentic Autofill: 'the AI agent and underlying LLM never need to see nor handle the credentials', with an approval prompt for each autofill and credentials injected over an end-to-end encrypted (Noise) channel. Auth0 Token Vault 'stores the access and refresh tokens for each connected account', and the app 'exchange[s] a user's valid Auth0 token for an external provider's access token'. The user explicitly approves scopes. Lesson: an IntoChat Secret is a handle such as secret://owner/<id> with a label. Only the neuron making the outbound call resolves it. OAuth tokens belong in one Token Vault neuron, not in each module's state (see K3).
Evidence: https://www.1password.dev/cli/secret-reference-syntax/; https://www.1password.dev/agentic-autofill; https://1password.com/blog/closing-the-credential-risk-gap-for-browser-use-ai-agents; https://learn.microsoft.com/azure/app-service/app-service-key-vault-references; https://auth0.com/ai/docs/intro/token-vault; https://auth0.com/blog/auth0-token-vault-secure-token-exchange-for-ai-agents/

### K18 (pattern, medium) Solid Pods, WAC and Verifiable Credentials: owner-held data with apps decoupled, per-origin access modes including Append, and selective disclosure
Solid: 'Users have personal online data stores called Pods … You choose which applications to use with your data', controlling 'which people, applications, and AI agents can read and edit them'. Web Access Control defines the modes Read, Write, Append ('add information, but not remove') and Control, and can grant by acl:origin, meaning per app. WAC is a W3C Community Group draft, not a Recommendation. The Verifiable Credentials Data Model 2.0 has been a W3C Recommendation since 15 May 2025, with issuer, holder and verifier roles, selective disclosure and data minimization. For example, an app can be shown 'over 18' without seeing the DOB. Lesson: the owner vault is the IntoChat equivalent of a pod. Append is useful for logs and lead lists. VC-style derived claims are a later-phase option.
Evidence: https://solidproject.org/about; https://solidproject.org/TR/wac; https://www.w3.org/TR/vc-data-model-2.0/

### K19 (pattern, high) PII classification should be driven by types first; detectors like Presidio are only a backstop for free text
Presidio has an analyzer (NER, regex, rules, checksums) and an anonymizer (operators including reversible encryption). It is now community-owned under the Data Privacy Stack, and it warns: 'because it is using automated detection mechanisms, there is no guarantee that Presidio will find all sensitive information.' .NET's DataClassification and redactor model applies redaction deterministically to anything tagged with a classification. Lesson: if every stored value carries a semantic type with a sensitivity class, redaction in logs, traces, signals and memory is deterministic. Detection is needed only for untyped chat text and tool outputs. The repo already has an UntrustedContentScreen for prompt injection, which is where a PII scan could sit.
Evidence: https://presidio.dataprivacystack.org/; https://learn.microsoft.com/dotnet/core/extensions/data-redaction; src/Modules/AI/AI/Clients/UntrustedContentScreen.cs:10-12

### K20 (risk, medium) GDPR requirements (special categories, portability, withdrawal of consent, erasure) collide with journaled or event-sourced storage and plaintext vector payloads
Art 9(1) singles out health, biometric, genetic, racial or ethnic origin, political, religious, trade-union, sex-life and orientation data. Art 20 requires export 'in a structured, commonly used and machine-readable format'. Art 7(3): 'It shall be as easy to withdraw as to give consent.' Art 17 covers erasure. The runtime already wires AddAzureBlobJournal. Orleans event-sourcing providers such as LogStorage 'replay the event sequence every time the grain loads', so a DOB written as an event persists in history after a 'delete'. Qdrant payloads and TextFieldChanged signals copy values too. Recommendation: sensitive values are stored only in the vault, encrypted with per-owner or per-item keys so that deleting the key erases them (crypto-shredding). Everything else holds references. Export is a vault operation over typed fields, and withdrawing a grant is one click. Crypto-shredding is an industry practice; it is not in the sources cited here.
Evidence: https://gdpr-info.eu/art-9-gdpr/; https://gdpr-info.eu/art-20-gdpr/; https://gdpr-info.eu/art-7-gdpr/; https://learn.microsoft.com/dotnet/orleans/grains/event-sourcing/journaledgrain-basics#state-transition-methods; src/Modules/DigitalBrain/Kernel/Aspire/DigitalBrainRuntimeHostingExtensions.cs:39; src/Modules/DigitalBrain/Kernel/Aspire/AzureOrleansJournalHosting.cs:9-19

### K21 (recommendation, medium) Recommended semantic type catalog shape: primitive + semantic type + sensitivity class + LLM exposure + widget mapping + validation, published as JSON Schema
Each catalog entry: {id, e.g. 'date' or 'person.birthDate'; primitive (string | integer | decimal | boolean | date | datetime | duration | binary | ref<T> | composite); validation (JSON Schema keywords: format, pattern, min and max, enum, contentMediaType); sensitivity (Public | Personal | SpecialCategory (GDPR Art 9) | Financial | Credential); llmExposure (value | masked | referenceOnly), where Credential is always referenceOnly and SpecialCategory defaults to masked; inputWidget and displayWidget, e.g. date → Calendar picker, email → email text box, money → currency input, file → upload, image → ImageCanvas, secret → obscured one-way field; redactor (erase, mask, or HMAC); indexable (whether it may enter vector memory)}. Starter set of about 22 types, the intersection of K7, K9, K11, K13, K14 and K15: Text, LongText, Integer, Decimal, Percent, Boolean, Date (date only), DateTime, Duration, Choice, MultiChoice, Email, Phone, Url, Money (amount + ISO 4217 currency), File, Image, Person (schema.org names, labeled contact points), PostalAddress, Location, Reference<Entity>, Secret (writeOnly). ### K22 (recommendation, medium) Where values live: an owner Personal Data Vault for personal and credential data, app-private state for everything else; addressable by ID, not a grain per value
(1) Owner Vault: one vault neuron per owner, possibly sharded by category. It holds typed fields keyed by semantic path (me.birthDate, me.email.work, me.address.home) and credentials (secret handles and OAuth grants; the Token Vault absorbs SalesforceState and GmailState tokens). It supports export (Art 20), erase (crypto-shred) and an audit log of every read, including reads by the assistant. (2) App-private state: each marketplace app's neurons hold their own domain data, such as LeadGenerator's leads. They hold references to vault items, plus cached copies only when a grant allows. Following AppEntity and EntityCollection, values that cross boundaries are addressable (stable ID, display label, resolver), but they are stored as fields of a vault or entity grain. A ValueNeuron<string> per value would multiply activations and storage writes without adding any consent or encryption benefit. On the owner's DurableGrain question: journaled durability suits the vault's audit trail, but secret payloads must be encrypted before they reach any journal (K20). Final grain-model choices belong to the Orleans/SDK stream.

## Open questions
- Is the Personal Data Vault per person only, or do we also need an organization or workspace vault (e.g. CRM customers from Supabase or Salesforce) with its own grants?
- Should marketplace apps ever receive raw personal values, or only references plus platform-rendered widgets? The strict option protects privacy but limits what third-party apps can compute.
- What should consent default to for a new app: ask each time, ask once and remember, or let the owner set a standing grant per semantic type?
- Which regulatory scope do we design for in v1 (EU GDPR, and which others)? Are special-category values (health, biometrics) allowed at all in v1, or blocked by the catalog?
- Are user-entered secrets such as raw API keys and passwords in scope for v1, or only OAuth connections through a central Token Vault?
- Should full LLM message capture in Aspire traces stay on by default in dev (today's behavior), or default to redacted, with opt-in per session?
- Deployment model: is IntoChat single-owner and local-first (desktop plus local Aspire), or a multi-tenant cloud? This decides key management for at-rest encryption: DPAPI or OS keychain vs Azure Key Vault or HSM.
- Should reading or writing vault data, and storing Files or Images, cost Compute? If so, is that charge approved together with the consent grant or separately?
- Are verified or derived claims (e.g. prove 'over 18' without revealing the DOB, W3C Verifiable Credentials) in scope, or deferred?
- Should app-private state be exportable and deletable through the same owner-facing GDPR flow as the vault, which would require every marketplace app to implement export and delete hooks?
