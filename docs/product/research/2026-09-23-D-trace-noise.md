# D-trace-noise

## Summary
I measured the running IntoChat AppHost read-only. The Aspire MCP list_traces tool shows only the latest 46 traces and hides the other 751, so I pulled every span with `aspire otel spans --format Json` and counted them with jq. The dashboard holds 797 traces and 4,874 spans. They cover only 3m09s, from 22:52:56 to 22:56:05Z, starting just after IntoChat launched. No spans arrived after 22:56:05 even though the app is still running and logs are still flowing. The most likely cause is that the Traces page was paused in the dashboard, which supports pausing each signal separately. That is not confirmed. In that window there was exactly one user intent, a POST /agent turn building the "person-card-form" behavior. It is 1 of 797 traces (0.13%) and 365 of 4,874 spans (7.5%). Of its 365 spans, 280 are one tool's poll loop and half of the rest are duplicates. My estimate is that fewer than 1% of all spans say something meaningful at product level.

Share of spans by cause:
- Flutter InboxBanner polling 6 endpoints every 2s, 5 of which are hard-coded 'e2e' demo widgets: 52.2%.
- BehaviorManager polling every 4s: 18.2%.
- Workspace-open N+1 GETs plus grain activations: 12.5%.
- The single agent turn: 7.5%.
- Orleans observer notifications appearing as their own root traces: 6%.
- A 404 retry storm on /chats/main/brain/events: 1.7% of spans but 10% of trace rows. The endpoint is written but never mapped.
- Startup extras (LLM warmup, dotnet CLI self-telemetry): 0.3%.

Across all of these, Orleans grain-call spans are 79.4% of everything. Every grain call produces 4 spans instead of 2, because activity propagation is registered twice: once by Aspire's Orleans integration (Orleans__EnableDistributedTracing=true) and once explicitly in DigitalBrainRuntimeHostingExtensions.cs:40. That alone accounts for about 40% of all spans. When nobody is using the app, it still emits about 1,440 spans/min and 240 traces/min, roughly 2M spans a day for one open client. At that rate the dashboard's default 10,000-trace limit is used up in about 42 minutes. Logs are worse. IntoChat has no logging configuration, so ASP.NET Core logs at Information. About 95% of console log entries are four lines written for every poll request, arriving at about 780 structured logs/min. The 10,000-log limit therefore holds only about 13 minutes. None of the logs still retained belong to a retained trace, so the agent run's logs are already gone.

Some noise is already handled. /health, /alive, Azurite HTTP calls and Azure Storage SDK spans are filtered, and the Orleans Runtime and Storage sources are not enabled, so there are 0 membership, reminder or storage spans. The larger problem is what is missing:
- **No GenAI data for the agent.** The agent path (AgentTurnRunner) builds its model client without the OpenTelemetry wrapper and calls tools directly. The /agent trace shows 16 bare HTTP POSTs to OpenAI with no model, token counts, tool names or cost. The only GenAI span is the startup warmup. The uncommitted AppHost.cs change that records message content therefore does nothing for the agent.
- **The owner's 'date' failure is split into many separate traces.** The behavior child process has no telemetry and receives no trace context from Deploy. Its 4 crash-loop retries of ITextField/Configure, which fail with "ArgumentOutOfRangeException (Parameter 'kind')" on textfield/date-of-birth, appear as 4 unrelated root traces. On top of those come 68 more observer-event root traces (60 LogsChanged, 8 Changed), all in 9 seconds.
- **No database, vector or MCP spans.** There is no Npgsql source, so the SQL behind "Show me all customers" is invisible. There are no Qdrant or MCP spans, and no product attributes (run, thread, workspace, tool, cost) anywhere.

A product-level trace should be one trace per user intent. The root is invoke_agent under POST /agent, carrying conversation, run and workspace ids, the model, total tokens and Compute cost. Under it come one 'chat {model}' span per model call and one 'execute_tool {name}' span per tool call, then one span per neuron call and one per database query. The behavior runtime and the UI render step link in through trace context or span links. That should come to about 15–45 spans, against 365 today. Steps: filter or remove the polling (or switch to server push), keep a single Orleans propagation registration, collapse in-process client/server pairs and poll loops, turn observer notifications into span events, tail-sample so every error or GenAI trace is kept and only a small share of the rest, and fix the generic span names.

### D6 (fact, high) [VERDICT: confirmed] Every Orleans grain call produces 4 spans because activity propagation is registered twice (~40% of all spans)
Aspire.Hosting.Orleans injects Orleans__EnableDistributedTracing=true by default, and I confirmed it in the IntoChat resource environment. When that flag is set, Orleans DefaultSiloServices calls builder.AddActivityPropagation(). DigitalBrainRuntimeHostingExtensions also calls silo.AddActivityPropagation() explicitly. AddActivityPropagation adds its grain-call filters with Add, not TryAdd, so both filter pairs run. The observed shape is Client→Client→(Server, Server): trace 2fc7a5fd has two nested IButton/Read client spans, then two sibling server spans under the inner one. Orleans RPC spans total 3,872 (Client 1,924, Server 1,948), 79.4% of all spans, and about 1,936 of them (≈40% of all spans) are pure duplicates. Calls from the external behavior process show a root server span plus a nested duplicate.
Evidence: src/Modules/DigitalBrain/Kernel/Aspire/DigitalBrainRuntimeHostingExtensions.cs:40 (silo.AddActivityPropagation()); aspire describe IntoChat-ytjajgyb → Orleans__EnableDistributedTracing=true; https://github.com/dotnet/aspire/blob/main/src/Aspire.Hosting.Orleans/OrleansServiceExtensions.cs (≈L455-458: 'Enable distributed tracing by default' sets Orleans__EnableDistributedTracing); https://github.com/dotnet/orleans/blob/main/src/Orleans.Runtime/Hosting/DefaultSiloServices.cs (≈L478-481: EnableDistributedTracing → AddActivityPropagation); https://raw.githubusercontent.com/dotnet/orleans/main/src/Orleans.Runtime/Hosting/CoreHostingExtensions.cs (AddOutgoing/IncomingGrainCallFilter, not idempotent); Trace 2fc7a5fdc335c356f6f63f1c33c701c5 parent chain: d1dba1fd → d7cfe079(C) → 96790801(C) → b6d1870c(S), 00ddcfad(S)

### D15 (fact, high) [VERDICT: partially] Sampling is 100% head sampling and cannot tell polls from intents; child dotnet CLIs also export spans
The root sampler is ParentBased(SuppressAzureStorageSampler(TraceIdRatioBased(SampleRatio ?? 1.0))). Telemetry:Tracing:SampleRatio is not set, so 100% of traces are kept. Separately, 'dotnet' child processes inherit the OTEL_* environment and export .NET SDK spans (telemetry-setup, parse, hostfxr-initialization). They show up as extra dashboard resources dotnet-cli-74fcdb88 and dotnet-cli-2d6d35ab (8 spans).

### D16 (pattern, high) Orleans observer notifications appear as their own root traces
Change and log notifications between neurons (IBehaviorProgramEvents.LogsChanged and Changed, ICodeDraftEvents.Changed) start new root traces (73 traces, 292 spans) and are not linked to the operation that caused them. LogsChanged fires once per behavior log line, so a crash loop multiplies the traces. Product-wise these belong as span events or links on the owning Deploy or Check span. They should be dropped unless an error occurred.
Evidence: Root traces: IBehaviorProgramEvents/LogsChanged roots=60 (22:54:34–22:54:43), Changed roots=8, ICodeDraftEvents/Changed roots=5; src/Modules/DigitalBrain/Behaviors/Behavior/Programs/BehaviorProgramNeuron.cs:11,53; src/Modules/DigitalBrain/Behaviors/Behavior/Execution/BehaviorSupervisor.cs:143

### D17 (recommendation, medium) Target: one trace per user intent, following the OTel GenAI conventions
'Show me all customers' should produce ONE trace:
- Root: HTTP 'POST /agent', or renamed 'chat.turn'.
- Under it: 'invoke_agent workspace-assistant' with gen_ai.agent.name, gen_ai.conversation.id=threadId, intochat.run.id, intochat.workspace.id, a pseudonymous user id, outcome (ok/failed/cancelled, reason), summed gen_ai.usage.input_tokens and output_tokens, and intochat.compute.units / intochat.compute.cost.
- Under that, in order:
  1. 'chat gpt-5.6…' with gen_ai.request.model, response.model, usage, finish_reason, cost.
  2. 'execute_tool supabase_schema' with gen_ai.tool.name, gen_ai.tool.call.id, isError. Beneath it one collapsed neuron span (e.g. 'ISupabase ReadSchema' with intochat.neuron.id), and beneath that 'db.query' (postgresql, db.query.summary, row count).
  3. 'chat …'.
  4. 'execute_tool show_supabase_query_table', with its neuron span, a SQL validation span, the table-view creation (columns, retry attempt as an event) and an 'IConversation Complete' span.
- UI render (Flutter 'GET /workspaces/{id}/tables/{tableId}' and pagination) is a separate request. It should carry the run id or a W3C traceparent from the SSE payload so it attaches as a span link or child 'ui.render table'.

### D18 (recommendation, medium) Noise-reduction plan: filter, collapse, sample, rename (ordered by impact)
Ordered by impact, with estimated effect on the measured window:
1. Collapse the duplicate Orleans propagation to a single registration: −40% of spans (D6).
2. Stop sending UI polling to telemetry. Either drop GET /ui/*, /behaviors polls and conversation reads in the AspNetCore Filter (children follow ParentBased), or better, replace polling with server push over SSE; the /brain/events endpoint already exists and only needs mapping (D5). Together −72%.
3. Collapse in-process grain Client+Server pairs into one span, and poll loops into one span with a poll.count attribute: agent trace 365 → about 40.
4. Emit Lifecycle spans (place/activate/register/OnActivateAsync) only above a duration threshold or on error.
5. Turn observer notifications into span events or links.
6. Tail-based sampling, for example in an OTel Collector or an in-process processor: keep 100% of traces with ERROR status, gen_ai.* or execute_tool spans, or latency above 1s, and a small probabilistic share of the rest.
7. Rename: unmatched 'GET' → 'GET (unmatched) 404'; the warmup root 'orchestrate_tools' → 'llm.warmup'; carry neuron identity as an attribute rather than relying on grain ids in target_id.
8. Logs: set Microsoft.AspNetCore and Azure.Core to Warning in IntoChat, and strip OTEL_* from spawned dotnet CLIs.
After steps 1, 2 and 8 the idle baseline goes from about 1,440 spans/min to near 0, and the 10k trace and log caps would hold days, not minutes.

### D20 (gap, medium) [VERDICT: partially] No telemetry basis for Compute pricing: tokens, model and cost are not on spans or metrics for agent runs

## Open questions
- Is the InboxBanner strip of five hard-coded 'e2e' widgets (chart, browser, video, expander, button) a product surface or a leftover test fixture? It is over half of all trace volume and could simply be removed or put behind a flag.
- Should the default developer trace view show only intent-level traces, with infrastructure spans (grain lifecycle, polls, observer events) available behind a toggle? Or should infrastructure spans be dropped at the source?
- Should prompts, tool arguments and results (customer rows, DOB, anything a user types) be recorded in traces by default in local dev (EnableSensitiveData=true)? If so, must the planned SDK type system mark Secret/PII values so telemetry redacts them?
- Is the Aspire dashboard meant to be the observability surface for app developers and marketplace publishers? Or should IntoChat ship its own 'activity timeline per intent', with Compute cost, built from the same spans?
- Should Compute billing come from a durable metering ledger correlated to traces by run/trace id, with telemetry used only for explanation and audit? Telemetry is sampled and evicted.
- Should UI freshness move from polling (/ui/* every 2s, behaviors every 4s) to server push, now that the brain/events SSE endpoint exists but is not mapped? Or should polling stay and just be filtered out of telemetry?
- Should behavior runtime processes (user and marketplace apps) run inside the caller's trace (Deploy → app process → neuron calls)? That decides whether a failing marketplace app shows up as part of the user's intent.
