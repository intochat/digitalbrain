# C-sdk-types-kernel

## Summary
The DigitalBrain kernel is small: about 2,000 lines of non-test code across Contracts, Kernel, Sdk, Mcp, Aspire and Aspire.Hosting. What a developer gets is a `Neuron` base class (an Orleans Grain plus live signal fan-out to observers), `Neuron<TState>` (a thin wrapper over IPersistentState with Snapshot and Save), a `Signal` record, `INeuron` (Watch/Unwatch), `IDigitalBrain` (`Get<T>(string id)` and `SubscribeAsync<T>`), `IModule` for compile-time composition, and some auth and webhook helpers in Sdk. The concepts named in the brief and in the repo's CONTEXT.md glossary do not exist in code today: IHandle, synapses, journals, entities and DigitalBrainClient.ConnectAsync. The owner approved deleting them on 2026-09-19, together with the old DurableGrain-based neuron. The glossary was never updated, which adds to "the product is hard to understand".

There is no type system for values. The 28 UI-kit contracts carry 62 string fields, and the one Date/Time-typed field in the whole kit is `DateTimeOffset? dueAt` on the Clock. Allowed values such as TextField kinds ('text','number','password','suggest') are private HashSets inside grains. The only thing the LLM sees is a CLR signature string (`Task Configure(String label, String kind)`), so it guessed 'date'. The only validator that checks a field kind rejected it, but only when the behavior ran after deployment. That is very likely the cause of the owner's card failure. A proto-vocabulary (text/number/date/boolean) exists, but it is copied into two internal classes in the Supabase and ClickHouse modules.

A date of birth has no typed, reusable home today. The Memory/Qdrant module stores free text and nothing outside its own module calls it, including the agent. Personal data therefore ends up in chat transcripts, in string widget values, or in Supabase rows. Secrets split in two:
- **Operator secrets** are handled well: LLM and API keys, the GitHub App key and the Supabase connection string are Aspire secret parameters, and module config rejects secret-like keys.
- **User OAuth tokens** are the weak spot. Salesforce access and refresh tokens are stored as plaintext fields in grain state. Gmail exchanges the code and then throws the tokens away. There is no vault; `ProtectedPayloadReference` is a pointer with no store behind it.

There is one owner login, and it is off by default. Integrations are global singletons, UI widgets are addressed by global names with no ownership check, and grain calls carry no caller identity. Tokens never appear in contracts, but an LLM-authored behavior (unsandboxed C#) can call any neuron by id. A 'password' TextField keeps its value in plaintext in state, in signals and in GET responses.

Persistence is mixed:
- Orleans IPersistentState in blob storage, using the binary Orleans serializer (opaque), in 42 places.
- One neuron (Agent) stores a JSON string inside that envelope.
- Behaviors and drafts use local-disk JSON; Memory uses Qdrant; Timer state is in memory only.
- Orleans Journaling 10.3.1-alpha.1 is fully wired: a blob container is provisioned and journal storage is registered in the silo. No grain uses it.

Checked against the dotnet/orleans v10.3.1 source, Journaling gives DurableGrain and keyed-injected IDurableValue<T>, IDurableDictionary, IDurableList, IDurableQueue, IDurableSet and IDurableTaskCompletionSource, plus a journal-backed IPersistentState. Each grain gets one append-blob journal that holds all its named states, stored as JSON Lines. It is prerelease only, and main has already renamed the core API.

Recommendation: do not make every value a neuron. The UI kit already works that way (one grain, one blob and one HTTP GET per widget), and it shows the costs: one activation, directory entry and blob per value, N+1 reads, no atomic update across fields, and lossy change signals. Orleans guidance is to size grains by domain entity.

Instead, define typed values in Contracts (Text, Email, Date, Money, Secret handle, FileRef, PersonRef) with schema, validation and UI hints, and store them as typed fields inside entity or document neurons, e.g. a Profile neuron holding `IDurableValue<Date> BirthDate`. Split neurons into three tiers: stateless (provider facades), snapshot (small, rarely written) and journaled (growing or append-heavy). The first journaled candidates are Workspace receipts, Agent history and events, and Conversation turns. A neuron should get its own identity only when it needs its own permissions, billing or observers; a Secret stored in a per-user vault neuron is the clearest example.

### C4 (fact, high) [VERDICT: partially] Grain state uses the binary Orleans serializer, not JSON, so stored data is opaque outside the runtime
The silo overrides Orleans' default JSON grain-storage serializer with OrleansGrainStorageSerializer, writing to blob container 'digitalbrain-v2-state'. Microsoft docs call binary 'opaque' and recommend JSON. Only AgentNeuron stores a real JSON document, as a string inside a binary envelope. Other data lives on local disk (behaviors, drafts, LocalFileStore) or in Qdrant (Memory). Consequence for the vector-DB goal: nothing can scan or index user data (e.g. a date of birth) at rest. Only code can read it by calling each grain.

> CORRECTION: The facts hold. The silo registers a keyed OrleansGrainStorageSerializer for 'Default' and container 'digitalbrain-v2-state' (DigitalBrainRuntimeHostingExtensions.cs:33-38). Orleans' PostConfigure picks up the keyed serializer by provider name (dotnet/orleans v10.3.1 src/Orleans.Core/Providers/IGrainStorageSerializer.cs, DefaultStorageProviderSerializerOptionsConfigurator.PostConfigure). AgentNeuron is the only grain storing a JSON string, inside AgentStorageEnvelope (AgentNeuron.cs:13-17, 258-263). The 'opaque, JSON recommended' wording comes from the ADO.NET persistence page. ### C6 (fact, medium) [VERDICT: confirmed] What Orleans Journaling v10.3.1 actually offers (checked against source)
DurableGrain : Grain resolves IJournaledStateManager, joins the grain lifecycle, and offers GetOrCreateState and WriteStateAsync. Keyed scoped services (any key) are registered for IDurableValue<T> (just `T? Snapshots happen when requested, when storage asks for compaction, or on format migration; the code has a TODO for a size-based policy. A failed write fences the manager. One WriteStateAsync coalesces all dirty states into one append; that is not a cross-grain transaction.

### C18 (recommendation, medium) Verdict on 'Text : ValueNeuron<string>': typed values yes, one neuron per value no
The cost of one grain per value: an activation, a directory entry and a journal or blob each. Every subscriber keeps it alive with one-minute Watch renewals. Reading a 20-field profile takes 20 calls. Cross-field atomicity needs Orleans transactions. Change signals are lost on reactivation. Orleans guidance is to size grains by domain entity (Users, Orders). Instead:
- Make Text, Date, Money etc. serializable value types in Contracts.
- Store them as typed fields inside entity or document neurons, e.g. a Profile neuron with `IDurableValue<Date> BirthDate` and `IDurableValue<Email> Email`, all appended to that neuron's single journal.
- Promote a value to its own neuron only when it needs its own identity, permissions, audit or billing, or many independent observers. A user's Secret in a vault neuron is the clearest example.

### C19 (recommendation, medium) Split neurons into three tiers (stateless, snapshot, journaled) rather than making all of them durable
Every neuron could technically be a DurableGrain, but it is a poor default. Two reasons:
- DurableGrain always resolves a journal manager and recovers state before OnActivateAsync. Stateless facades (18 LLM grain types, Supabase, ClickHouse, Dotnet, Timer) would pay a storage round-trip per activation for nothing.
- C# single inheritance means Neuron cannot both stay a plain Grain and also be a DurableGrain.

Proposed tiers:
- **Stateless**: Neuron.
- **Snapshot**: Neuron<TState>, for small, rarely written state such as widgets and connection records.
- **Journaled**: a JournaledNeuron : Neuron that copies DurableGrain's three lines of lifecycle wiring, for growing or append-heavy state.

There is a cheap migration seam: journaling registers IPersistentState<> as a keyed service backed by DurableState<>, so Neuron<TState> subclasses could switch storage by changing only the constructor attribute.

### C21 (risk, high) [VERDICT: confirmed] Kernel semantics that typed values would inherit: change events can be lost, and a failed write is not rolled back

### C24 (recommendation, medium) Proposed shape of an SDK type system
1. **Value types in DigitalBrain.Contracts** ([GenerateSerializer]): Text, Email, Phone, Url, Date (DateOnly), DateTime, Money(amount, currency), Quantity, FileRef/ImageRef (asset handles), PersonRef (neuron handle), and Secret (an opaque handle, never the plaintext). 4. **The contract catalog publishes schemas and descriptions.** They are indexed into Memory's reserved 'digitalbrain.capabilities' namespace so the assistant can search neurons and types.
5. **Entity neurons such as a Profile store fields** as IDurableValue<T> through the journaled tier.

## Missed (from verifier)
- Most UI-kit neurons cannot be displayed in the live client. Composition accepts only 9 child kinds (CompositionValidation.cs:11), and NeuronView renders only surface/layout/text/button/textfield/tabs/card/collection/imagecanvas. Every other kind shows 'This component cannot be displayed.' (src/Modules/Google/Flutter/app/ui/lib/src/composition/neuron_view.dart:123-356). Outside the gallery and tests, Dart code never references 'person', 'calendar', 'slider', 'toggle', 'rating', 'progress', 'infobar', 'tree' or 'color'. IPerson and ICalendar have C# grains, persistent state and /ui HTTP endpoints but no client renderer. So binding typed values (Person, Date) to UI-kit widgets has no front end to land on today. Confidence: medium-high.
- Password kind mismatch between C# and Dart. TextFieldNeuron accepts only 'password' (TextFieldNeuron.cs:15), but the Flutter renderer obscures input only when kind == 'secret' (neuron_view.dart:184). A 'password' field is therefore shown in cleartext, and a 'secret' field is rejected by the server. This strengthens C14 and is a concrete example of the magic-string problem in C8.
- Kernel semantics gap in multi-silo deployments. When a LocalSignalHub exists (inside a silo), SignalSubscription.ConnectAsync registers only with the local hub and returns without Watch or lease renewal (SignalSubscription.cs:48-53). Neuron.PublishAsync publishes to the hub on the silo hosting the grain activation (Neuron.cs:32). An in-silo subscriber (IntoChat endpoints, coordinators) therefore silently misses signals from grains activated on another silo, and never gets the 'Neuron reactivated' failure that out-of-silo clients get. This is harmless with one silo but matters for any scaled 'OS' deployment.
- The contract catalog's module list is hard-coded to four IDs. CodingModule.cs:48-54 registers only time, flutter, ai and google (Gmail) as selectable module IDs for code_contracts. Memory, Supabase, ClickHouse, Salesforce, GitHub and Behavior contracts cannot be selected by ID. They appear only in the unfiltered modules=[] catalog, which sorts AI last and truncates at 24,000 chars (ContractCatalog.cs:30, 65-66). Discovery is therefore not driven by which modules are installed. This matters for 'the assistant can find any part of the system'.
- IDurableValue<T> tracks changes only on assignment. DurableValue<T> sets _isDirty only in the Value setter (dotnet/orleans v10.3.1 src/Orleans.Journaling/DurableValue.cs). Mutating a reference-type T in place (e.g. value.Street = ...) is not journaled. A ValueNeuron<T> design must require immutable values (records) or reassignment. Also note the snapshot trigger: Azure blob journal storage requests compaction only at 49,000 append blocks (src/Azure/Orleans.Journaling.AzureStorage/AzureBlobJournalStorage.cs:37,48), and the manager otherwise just appends (JournaledStateManager.cs:258 TODO). A chatty value grain can accumulate a long replay on activation. v10.3.1 also ships Azure Table and Redis journal storage, not only append blobs.
- The approved 2026-09-19 spec is only partly implemented in the kernel. Spec :108 says 'Start without a generic Neuron<TState> wrapper', yet Neuron<TState> exists and 24 widgets use it. Spec :109 requires reload or deactivate after a failed persistence write, which Neuron<TState>.Save does not do (Neuron.cs:48-51); this is the root of C21. Spec :120 says to prefer explicit composition over string-loaded types, hosting attributes and projections, yet LoadModules uses Type.GetType (DigitalBrainRuntimeHostingExtensions.cs:67-88), AddModuleType uses ModuleHostingAttribute plus Type.GetType (DigitalBrainHostingExtensions.cs:79-89), and projections remain. The planning doc should treat these as open debt, not settled design.
- Sensitive data in telemetry by default during development. AppHost sets AIOptions.Telemetry.EnableSensitiveData = true in Development run mode unless configured otherwise (AppHost.cs:38-42), so full prompts, model outputs and tool arguments and results go into GenAI traces in the Aspire dashboard. A date of birth or password typed into chat, and Supabase rows returned by tools, therefore end up in traces. This is relevant both to 'can secrets reach the LLM or telemetry' and to the owner's 'too much trash in Aspire traces'.
- GmailNeuron publishes GmailConnected even though it discards the tokens it just exchanged (GmailNeuron.cs:28-35). The UI and signals report a successful connection that will not survive any subsequent call. This makes C12's Gmail point a user-visible correctness bug, not just a storage gap.

## Open questions
- Should durable (journaled) state come back into the kernel as an opt-in tier, reversing part of the 2026-09-19 simplification, given that Microsoft.Orleans.Journaling is prerelease-only and its API has already been renamed on main?
- Is a 'value' something with its own address (ValueNeuron with its own ID, ACL, billing and subscribers), or a typed field on an entity such as Profile.BirthDate? Which concrete values, if any, need their own identity (secrets? shared counters?)
- Is IntoChat a single-owner personal OS for now, or must multi-user and tenants (per-user vault, per-user integrations, per-user Compute billing) be kernel-level before the marketplace? Today Salesforce, Gmail and GitHub are one global connection each.
- Secret policy: may the LLM ever see a secret's plaintext (e.g. to fill a form)? Should an app get a secret only through a user-approved grant that a provider neuron resolves?
- Which value types ship in v1 (Text, Email, Phone, Url, Date, DateTime, Money with currency, Secret, File, Image, PersonRef, Location)? Who owns their UI rendering (the Flutter kit) and their validation?
- Trust model for marketplace apps: must third-party code run sandboxed out of process (behaviors today are explicitly not a sandbox and can call any neuron by ID)? May apps define new grain types (which would need namespacing), or only compose installed ones?
- Is it acceptable to start fresh on stored state (as on 2026-09-19) in order to switch grain storage from the opaque binary serializer to JSON or journaled JSON Lines, so user data becomes inspectable and indexable?
- Is personal data such as a date of birth scoped to the user (across workspaces) or to a workspace? Today workspace scope = hash(owner, workspaceId).
