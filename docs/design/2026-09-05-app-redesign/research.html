01 / UI foundation

Choose controls by capability.
Create the atmosphere ourselves.

A component library supplies buttons, menus, input, focus behavior and overlays. Our UI kit gives those parts one identity. The graph, assistant presence and subscription model remain DigitalBrain components.

Recommended direction

Forui, behind our own UI kit.

A neutral foundation for desktop and touch, with the overlays and inputs this app needs. Add a restrained glass or tactile surface system through our own tokens.

Foundation → Forui controls and overlays
Identity → DigitalBrain color, type, depth and motion
Graph → Custom rendering and real domain state

Glass is a surface treatment.

Flutter supports backdrop blur directly. Apply it to a few floating surfaces—the composer and inspector—while keeping text and controls crisp. Avoid nested blur on every animated neuron.

Tactile does not have to mean faint.

Use soft depth on large surfaces and clear outlines for controls. Selected, focused, disabled and active states must be distinguishable without depending on shadows or color alone. This is a design constraint for our finished kit.

02 / The experience

Open the app.
Meet Ino. See what happens.

The startup view is a useful graph, not a dashboard to configure. The latest response and bottom composer make conversation immediate; deeper detail appears when the user asks for it.

01

A graph worth looking at

Group neuron instances by module. Use recognizable service icons, short labels and a precise activity line such as “Reading 3 documents.” Show active work clearly while leaving idle capability in the background.

02

One conversation, two depths

Keep the composer anchored at the bottom and show the latest assistant response above it. “Conversation” opens the full durable transcript. Never throw away older messages to create a minimal screen.

03

Every object can explain itself

Select a neuron for its purpose, current state, recent activity and subscriptions. Select an edge for its direction, signal type, binding and recent deliveries. Put raw identifiers and payloads behind a secondary detail view.

04

Activity is observable

A pulse means a signal was observed. “Searching” means a search operation started. Waiting for a model response is distinct from running a tool. Ino’s presentation follows these events.

05

A readable icon vocabulary

Each neuron has a type icon, optional provider mark and label. Gmail, Salesforce and Aspire get curated assets. Unknown types get a consistent fallback. An icon represents capability; it does not imply a subscription.

06

Focus without losing place

Inspect in a side panel instead of navigating away. Keep graph positions stable through activity updates. Let users pan, zoom, fit the graph and return to the active work without constantly moving their camera.

Empty, disconnected and waiting states are part of the design. Show what is connected and when data was last observed. Preserve the last known graph as visibly stale during a disconnect; stop activity pulses and distinguish reconnecting from idle.

03 / Ino in motion

One expressive presence.
A quiet system around it.

Give the assistant personality without making every integration into a cartoon. Ino receives the rich animation; tools and documents use small, functional feedback.

A stateful animation runtime with data binding, state machines, six-platform support and an MIT runtime license. Bind the persona to a small presentation model. Current Rive guidance recommends data binding for new work over legacy inputs.

04 / A truthful graph

The visual model must follow
the system’s actual rules.

Keep topology, traffic and presentation distinct. That makes the graph useful for understanding the system, rather than an animated approximation of it.

TopologyModules contain neurons. A neuron owns its outgoing synapses.
ActivityObserved signals and turn states describe work occurring over time.
ProjectionStable identities and ordered updates produce a coherent visible state.
PresentationIcons, labels, pulses and Ino motion make that state understandable.

A synapse is a connection.

A signal is what crosses it. The edge inspector should show its source, destination, signal contract, binding and recent delivery records. A selected signal can reveal a useful payload summary, timestamp and outcome.

Expose “Subscribe” and “Unsubscribe” where meaningful. Show a pending change until the system confirms the resulting state.

Bound and Learned have different meaning.

Bound: an explicit source-owned subscription. Unsubscribe removes that connection. Broadcast follows existing matching outgoing edges.

Learned: a connection reinforced through handled direct delivery. A handler’s capability alone does not create a subscription or default broadcast fan-out.

Renderer choice follows the interaction.

For readable layered graphs, ordinary Flutter node widgets over CustomPainter and InteractiveViewer support custom edge hit-testing, pan/zoom and semantics. Keep an optional 3D renderer behind the same view model.

The current three_js 0.3.0 is a rendering engine, not a domain graph. Its documentation lists platform-specific limitations. GraphView 1.5.1 can help with small-graph layouts, but is not a realtime topology or subscription engine.

Accessible exploration is first-class.

  • Keyboard focus and selection for neurons, edges and inspector actions.
  • A searchable text/list alternative to spatial navigation.
  • Reduced-motion mode: retain state changes, replace travel pulses with static emphasis.
  • Clear focus rings, readable contrast and labels beyond icon or color.
  • Inspect without reordering focus or announcing every animation frame.

Flutter accessibility guidance ↗Forui interaction primitive ↗

The HTML concepts use local simulated scenarios. They demonstrate interaction and visual direction; they do not connect to Gmail, Salesforce, Aspire, DigitalBrain or a model. Live activity must come from the system when implemented in Flutter.

05 / The migration

A complete visual change.
A deliberate implementation.

Make the new experience real in thin, verifiable slices. Keep working capabilities available as the presentation changes.

Select the direction and define the UI-kit contract.

Choose one concept, then establish typography, color, spacing, surface, focus and motion tokens. Build product-level components so application screens depend on DigitalBrain vocabulary rather than a third-party library API.

Replace the shell while preserving chat delivery.

Move the working composer and durable conversation state into the graph-first layout. Retain accepted command identity, streamed deltas, journal reconciliation and visible failure handling. Add the latest-reply presentation and an expandable transcript.

Connect topology, inspection and activity.

Use authoritative neuron and synapse state plus observed activity. Implement subscription changes through the existing source-owned commands. Validate reconnects, stale projections, ordering and activity completion before adding visual polish.

Add Ino and verify the finished experience.

Audit existing Rive assets, map observed states and add reduced-motion behavior. Verify keyboard navigation, edge selection, readable payload summaries, window resizing, long responses and Windows performance while real chat and graph updates run together.
