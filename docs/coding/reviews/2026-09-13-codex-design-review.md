# Codex adversarial review of coding-agent-design.md (2026-09-13)

Run with `codex exec` (codex-cli 0.154.0) against the proposal at commit 08b4951e. Each finding is folded into the design; section 8 of the design records the disposition.

1. **[blocker] §4.4: starting standby already creates competing reminder execution.** A has pending work and a `retry` reminder. B starts with the same `ServiceId`; its independent reminder service reads the same reminder rows and activates the same neuron. This happens **before YARP switches traffic**. Azure reminder queries partition by `ServiceId`, without filtering normal reads by `ClusterId`; both clusters can process the retry. One can also unregister the shared reminder while the other still needs it. **Smallest fix:** introduce exclusive active-slot ownership covering reminder execution, background work and mutations; standby must remain fenced until A relinquishes ownership. [Provider source](https://github.com/dotnet/orleans/blob/main/src/Azure/Orleans.Reminders.AzureStorage/Storage/RemindersTableManager.cs)

2. **[blocker] §4.4: shared journals do not transfer activation ownership or make rollback safe.** A’s `refactoring` activation remains alive while B’s smoke turn activates the same identity. Both recover state and attempt progress. Conditional journal appends can reject the competing writer; they do not migrate its continuation or prevent external effects performed before persistence. Switching back to A also exposes cached state predating B’s writes, potentially with an incompatible schema. **Smallest fix:** enforce one writer across snapshots and journals, discard old activations before reactivation, and require backward-readable state throughout the rollback window. Pin and verify the alpha provider’s behavior; current source demonstrates conflict detection, not cross-cluster orchestration. [Journal implementation](https://github.com/dotnet/orleans/blob/main/src/Azure/Orleans.Journaling.AzureStorage/AzureBlobJournalStorage.cs)

3. **[blocker] §4.4: reconnecting SSE cannot resume an unfinished MAF run.** A executes a tool, then promotion stops A before `AgentNeuron` reaches `SessionStateAsync` and `SaveAsync`. B has the previous session and pending reaction, so recovery can repeat the model call and tool effect. An existing SSE request stays attached to A; reconnecting does not restore its call stack or missing events. The workspace `/agent` path also explicitly says it has no chat neuron. **Smallest fix:** persist a run ID, tool-operation IDs/results and replayable output events; reconnect by run ID and cursor. Execute swap as a durable follow-up after the initiating turn commits. Session serialization alone preserves conversational state. [MAF serialization design](https://github.com/microsoft/agent-framework/blob/main/docs/decisions/0018-agentthread-serialization.md)

4. **[major] §4.2/D1: hosted-service registration is too late to guarantee MSBuild isolation.** Another module loads `Microsoft.Build.Framework` before warmup. `IsRegistered` remains false, but `RegisterDefaults()` now fails because MSBuild assemblies are already loaded. The proposed global `DisableMSBuildAssemblyCopyCheck` additionally permits application-local binaries to compete with SDK binaries; an incompatible MSBuild/NuGet dependency can fail at its first API call. Neither Orleans nor ASP.NET inherently causes this, but the design leaves the ordering uncontrolled. **Smallest fix:** register at the executable entry point before host composition, select the intended SDK explicitly, and remove conflicting runtime assets instead of globally suppressing the check. Use D1’s worker process if the host needs incompatible versions. [Locator source](https://github.com/microsoft/MSBuildLocator/blob/main/src/MSBuildLocator/MSBuildLocator.cs)

5. **[major] §4.2/D1: successful Locator registration does not prove BuildHost can load this solution.** The standby output lacks part of `BuildHost-netcore`, or its child process cannot resolve the required runtime/SDK. **`OpenSolutionAsync` breaks when launching/evaluating through BuildHost**, regardless of the silo’s successful startup. The phase 0 loader also accepts any nonzero project count despite recorded failures, allowing a partial solution to become `Ready`. **Smallest fix:** validate the complete BuildHost payload and SDK selection in the actual slot output, then require the expected project set and successful reference resolution before declaring semantic readiness.

6. **[major] §4.2/D1: Roslyn memory pressure can take down the agent hosting it.** A broad reference/diagnostics query materializes compilations while older snapshots remain referenced by edits; B simultaneously warms another workspace and a build runs. Compilation objects remain in the silo even though project evaluation uses BuildHost. Under Windows memory pressure, GC stalls or allocation failure affect Orleans and ASP.NET too. **Smallest fix:** move `SolutionWorkspace` behind the existing loader/service seam into a restartable process with a memory limit and bounded concurrent semantic queries. Keep durable status and map data in the neuron.

7. **[major] §4.2/D3: isolated outputs do not produce a coherent source snapshot.** A solution open reads project A, an edit/checkout changes the tree, then it reads project B. The resulting model mixes generations. Separately, slot restore writes assets under `ArtifactsPath`, while the proposed parameterless `MSBuildWorkspace.Create()` can evaluate against ordinary `obj` paths and stale assets. **Smallest fix:** analyze and build a fixed worktree generation with identical SDK, configuration and intermediate-path properties. Validate that generation before applying edits. `TryApplyChanges` is not an atomic transaction over multiple filesystem writes.

8. **[major] §4.5/D4: model-driven manager replay changes decisions and multiplies cost.** `ChatNeuron.SelectAsync` constructs a manager and calls selection `Turn + 1` times, always using the **current full transcript**. Replacing round-robin with an LLM therefore regenerates historical choices using later information. Across 25 invitations, that is **325 selection calls**, before participant calls; growing transcripts compound token cost. **Smallest fix:** persist each selected speaker and termination decision. Make exactly one new selection per completed turn, using a bounded summary and unresolved-needs list.

9. **[blocker] §4.5: awaiting a peer’s answer inside a reaction can prevent the question from being sent.** A chair tool fires a question through `AgentNeuron.FireSignalAsync`, then waits for the peer’s reply before returning. `Announce` only buffers the question; `Neuron<TState>` persists and dispatches it after the reaction saves. The model run waits for an answer to an undispatched question, while serialized reactions prevent a reply reaction from completing the wait anyway. Existing fire-and-return behavior avoids this. **Smallest fix:** tools return an announcement receipt immediately; save a “waiting for X” phase and continue in a later correlated reaction. Do not implement synchronous peer conversations or approval waits.

10. **[major] §4.5: the participant protocol cannot support the proposed roster unchanged.** When the manager selects the owner’s `uichat`, it sends AI vocabulary `Turn`; UI `ChatNeuron.ReceiveAsync` has no handler producing the required `Said`, so `PendingParticipant` never clears. Also, re-instructing the chat during scope expansion changes synapses but does not update the active run’s persisted `RunPolicy.Participants`; newly added file agents remain unselectable. **Smallest fix:** keep `uichat` as an observer/approval endpoint and add an explicit roster-update transition for the active run.

11. **[major] §4.5: transcript retention can erase context entirely, while sessions repeatedly duplicate it.** Both `TranscriptAsync` and `TurnContextAsync` call `ReadJournal(Incoming, 0)` and consume only `Delta`. Once retention advances past the beginning, `JournalWindow.Read` returns a gap/reset with **an empty delta**. The chair loses the request and discussion. Before that boundary, each returning file agent receives the entire transcript again inside its already-persisted session, increasing context and cost. **Smallest fix:** maintain a task transcript checkpoint plus cursor, handle reset explicitly, and send each agent only a bounded summary and unseen messages.

12. **[blocker] §4.3/D7 and phase 0 Task 7: the proposed graph passes its parser test but still cannot open.** `code_map` returns `name`; [`WorkspaceApp._accept`](E:/intochat/digitalbrain/src/Modules/UI/Flutter/shell/lib/workspace/workspace_app.dart:255) requires `id` and silently returns without it. Task 7 also misses the separate automatic-opening kind whitelist in `workspace_chat.dart`. Finally, marking every graph `_servedByResult` assumes complete node/edge data, whereas an `IGraph` card reference requires fetching it. **Smallest fix:** return a stable artifact `id`, update both opening paths, and distinguish inline graph snapshots from graph references with a read route. Verify tool-event → artifact acceptance → editor, rather than testing only the parser.
