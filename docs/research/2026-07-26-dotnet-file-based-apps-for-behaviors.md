# .NET file-based apps as DigitalBrain Behavior programs

Research date: 2026-07-26

## Recommendation

Use a .NET 10 file-based app as the **authoring and compilation format** for each Behavior
revision, but do not use `dotnet run behavior.cs` as the production execution loop.

An approved revision should be one immutable `.cs` source file plus a manifest. An isolated build
worker compiles that file once as a library against exact, allowlisted DigitalBrain contract
packages. A separately isolated runtime worker loads the resulting assembly and speaks only to a
trusted capability broker. `BehaviorNeuron` remains the trusted Orleans neuron that owns identity,
incoming and outgoing synapse journals, revision selection, private durable state, and lifecycle
facts. The source program does not inherit `Neuron`.

This preserves the product model—ordinary C# over neuron contracts—without confusing a convenient
SDK source format with a security boundary or paying restore/build cost on every invocation.

## What a file-based app is

.NET 10 file-based apps are ordinary compiled C# applications whose project is generated by the
SDK. They are not interpreted scripts. On the first invocation, the `dotnet` host generates a
virtual project, compiles the source, stores the artifacts under the user's temporary
`dotnet/runfile` tree, and executes the output. A subsequent unchanged invocation can run the
cached executable without rebuilding. The C# tutorial explicitly says these are not script files.
([File-based apps](https://learn.microsoft.com/en-us/dotnet/core/sdk/file-based-apps),
[C# tutorial](https://learn.microsoft.com/en-us/dotnet/csharp/fundamentals/tutorials/file-based-programs),
[SDK design](https://github.com/dotnet/sdk/blob/release/10.0.4xx/documentation/general/dotnet-run-file.md))

This is distinct from two similarly named mechanisms:

- **C# scripting** is a different compilation model. The SDK design deliberately chose normal C#
  plus a virtual project so a file can be converted to a conventional project without changing
  language semantics.
- **Single-file deployment** is a publish option that bundles application files into one
  OS/architecture-specific deployment binary. It says nothing about whether the source started as
  one `.cs` file and provides no isolation.
  ([Single-file deployment](https://learn.microsoft.com/en-us/dotnet/core/deploying/single-file/overview))

## Supported authoring surface

The unambiguous invocation is:

```text
dotnet run --file behavior.cs -- <arguments>
```

`dotnet run behavior.cs` and `dotnet behavior.cs` are shortcuts. The `--file` form matters when a
project exists in the current directory: without it, compatibility rules can interpret
`behavior.cs` as an argument to that project. On Unix, direct execution uses
`#!/usr/bin/env -S dotnet --`, LF line endings, no BOM, and executable permission. There is no
equivalent Windows shebang execution.

The documented directives, placed at the top of the file, are:

```csharp
#:sdk Microsoft.NET.Sdk
#:property TargetFramework=net10.0
#:property OutputType=Library
#:package DigitalBrain.Behaviors.Contracts@1.0.0
#:project ../Some.Module.Contracts/Some.Module.Contracts.csproj
```

- `#:package Name@Version` creates a NuGet package reference. A missing version is valid only when
  central package management supplies it; `@*` selects the latest version.
- `#:project path` creates a project reference and therefore works for repository-local module
  contracts.
- `#:property` sets an MSBuild property.
- `#:sdk` selects the SDK; `Microsoft.NET.Sdk` is the default.
- `#:include` adds source/resources/content and is available in .NET SDK 10.0.300 and later (and
  .NET 11 Preview 3 and later). Globs currently disable file-app build caching.

The public .NET 10 Learn page does not document a general raw-assembly directive. Current SDK
design/source maps an included `.dll` to an MSBuild `Reference`, and an experimental `#:ref`
directive compiles another `.cs` file as a separate virtual project. Neither is a sound product
contract today: the public documentation lags the SDK source, and `#:ref` remains feature-gated.
DigitalBrain should therefore use exact NuGet packages for installed module contracts and
`#:project` only for source-controlled development. Do not make raw DLL inclusion or `#:ref` part
of the Behavior format yet.
([Directive reference](https://learn.microsoft.com/en-us/dotnet/core/sdk/file-based-apps),
[current SDK design](https://github.com/dotnet/sdk/blob/release/10.0.4xx/documentation/general/dotnet-run-file.md))

## Restore, build, cache, publish, and diagnostics

- `dotnet restore behavior.cs` restores packages. Restore is implicit in `build`, `run`, and
  `publish` unless `--no-restore` is supplied.
- `dotnet build behavior.cs` creates a virtual project and compiles it. By default output is under
  `<temp>/dotnet/runfile/<name>-<hash>/bin/<configuration>/`; `--output` or
  `#:property OutputPath=...` makes the destination explicit.
- `dotnet build behavior.cs` followed by `dotnet run behavior.cs --no-build` is the documented way
  to compile once before concurrent development invocations. Direct production execution should
  use the built artifact or a published deployment: Microsoft explicitly advises against
  `dotnet run` in production.
- File-app caching considers source content, directives, SDK version, and implicit build files.
  Microsoft documents edge cases where implicit-file changes or moving a file can confuse the
  cache. `dotnet clean behavior.cs`, `dotnet clean file-based-apps`, and then a fresh build are the
  recovery path. The SDK design also documents `--no-cache` and
  `DOTNET_CLI_CONTEXT_VERBOSE=true` for cache decisions.
- `dotnet project convert behavior.cs` materializes an equivalent conventional project beside a
  copy of the source. This is useful for inspecting the generated project model, not part of the
  install path.
- `dotnet publish behavior.cs` is supported and file-based apps enable Native AOT by default.
  DigitalBrain should set `PublishAot=false`: the Behavior is a loadable library hosted by a
  worker, not an independently launched native application, and its contract/IPC proxies may use
  dynamic features.

File-based apps inherit `Directory.Build.props`, `Directory.Build.targets`,
`Directory.Packages.props`, `nuget.config`, and `global.json` from their directory tree.
Microsoft recommends keeping them outside conventional project cones and controlling the implicit
files around them. For DigitalBrain this is stronger than an organization tip: every build must
use a fresh isolated directory with a pinned SDK and system-owned build configuration.
([File-based apps](https://learn.microsoft.com/en-us/dotnet/core/sdk/file-based-apps),
[`dotnet run`](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run))

## Security finding

File-based apps are full-trust .NET programs. Their source directives can select SDKs and NuGet
packages, and their build inherits and executes MSBuild targets. Therefore the **compiler/restore
step is untrusted too**, not only the resulting program. Syntax allowlists and Roslyn analyzers are
admission checks, not containment.

Modern .NET has no supported in-process sandbox for unknown code. Code Access Security and
security transparency are not supported as security boundaries, and additional `AppDomain`
isolation is unavailable. Microsoft directs applications toward OS permissions, separate
processes, containers, or virtualization.
([Secure coding guidelines](https://learn.microsoft.com/en-us/dotnet/standard/security/secure-coding-guidelines),
[unavailable .NET Framework technologies](https://learn.microsoft.com/en-us/dotnet/core/porting/framework-overview))

`AssemblyLoadContext` solves dependency loading/versioning and can support cooperative unloading.
It is not a hostile-code boundary: Microsoft states that it provides no security features and code
has the permissions of its process. Dependencies also have no binary isolation from each other.
([AssemblyLoadContext API](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.loader.assemblyloadcontext),
[AssemblyLoadContext concepts](https://learn.microsoft.com/en-us/dotnet/core/dependency-loading/understanding-assemblyloadcontext),
[plugin tutorial warning](https://learn.microsoft.com/en-us/dotnet/core/tutorials/creating-app-with-plugin-support))

For a Windows worker, the documented native boundary is an AppContainer or stricter
Less-Privileged AppContainer. It restricts credentials, files/registry, network, devices, windows,
and other processes according to granted capabilities. Put the process tree in a non-breakaway Job
Object for CPU, memory, process-count, and time limits and kill-on-close. A Job Object supervises
resources; it does not replace AppContainer privilege isolation. Strong hostile multi-tenant
deployment requires a stronger boundary such as Hyper-V-isolated containers.
([AppContainer isolation](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation),
[launching AppContainer/LPAC](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer),
[Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects),
[Windows container security](https://learn.microsoft.com/en-us/virtualization/windowscontainers/manage-containers/container-security))

## Proposed DigitalBrain execution shape

```text
proposal source + manifest
        |
        v
isolated build worker -- restore from allowlisted/offline packages
        |                 compile once; run BDD proofs
        v
immutable revision artifact (source, manifest, DLL, deps, PDB, diagnostics, hashes)
        |
human approval and owner-scoped installation
        |
BehaviorNeuron -- journal trigger/start/result/failure and own durable state
        |
trusted broker -- validate owner, revision, contract, method, target, arguments, delegation
        |
sandboxed runtime worker -- load only the approved DLL; no Orleans credentials
        |
module capability calls over authenticated, ACL-restricted IPC
```

The installed source should have a system-generated, canonical header. The proposal body must not
be allowed to introduce its own `#:sdk`, `#:project`, `#:include`, arbitrary `#:package`, or build
properties. The manifest selects exact module-contract versions from the compiled module catalog;
the installer writes pinned package directives. Never use `@*` for an approved revision.

Compile as a library:

```csharp
#:property TargetFramework=net10.0
#:property OutputType=Library
#:property PublishAot=false
#:package DigitalBrain.BehaviorSdk@1.0.0
#:package DigitalBrain.Modules.Flutter.Contracts@1.4.2

public sealed class StartUi : IBehaviorProgram<DigitalBrainActivated>
{
    public async ValueTask ExecuteAsync(
        DigitalBrainActivated input,
        IBehaviorContext brain,
        CancellationToken cancellationToken)
    {
        var shell = brain.Get<IShell>("desk");
        var command = brain.DeterministicCommandId("open-login");
        await shell.Open(
            new OpenScene(command, "login", "Sign in"));
    }
}
```

`IBehaviorContext` is an IPC-backed programming model, not an Orleans client and not
`IGrainFactory`. The runtime worker receives no cluster credentials. Each requested module call is
sent to the trusted broker, which performs exact catalog and permission checks before the
owner-scoped Orleans call. Behavior-local intent input, output, and state should cross IPC as
schema-validated data; only module-owned compiled CLR contracts cross the typed module boundary.

On Windows, an ACL-restricted named pipe is a plausible broker transport. The default pipe ACL is
too broad; authorize the worker identity/AppContainer SID explicitly. Launch with
`UseShellExecute=false`, drain stdout/stderr asynchronously to avoid deadlocks, and treat
`WaitForExitAsync` cancellation as cancellation of the wait—not termination of the worker. Close
the Job Object or terminate the process tree on timeout.
([Named-pipe security](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights),
[`PipeOptions.CurrentUserOnly`](https://learn.microsoft.com/en-us/dotnet/api/system.io.pipes.pipeoptions),
[`UseShellExecute`](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.processstartinfo.useshellexecute),
[redirected-output deadlocks](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.processstartinfo.redirectstandardoutput),
[`WaitForExitAsync`](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.process.waitforexitasync))

## Strongest counterargument

This design introduces two out-of-process systems—a build sandbox and a runtime sandbox—plus
artifact storage and IPC. That is materially more operational complexity and latency than compiling
and loading a source file in the Orleans silo.

The simpler in-process design is acceptable only for source-controlled, signed built-in
Behaviors. It is not an acceptable basis for AI-generated or community code: `AssemblyLoadContext`
cannot contain a malicious assembly, and compilation itself can run restore/MSBuild extension code.
The execution abstraction can remain identical while provenance selects
`TrustedInProcessBehaviorExecutor` or `SandboxedBehaviorExecutor`.

## Uncertainties to resolve with prototypes

1. **Deployment boundary:** AppContainer/LPAC is Windows-specific. The Linux and cloud threat model
   must choose an equivalent OS/container/VM boundary before installed Behaviors ship.
2. **Worker lifetime:** start one sandbox per execution first for clear cancellation and isolation;
   measure before considering a recyclable one-revision worker pool.
3. **Contract packaging:** decide whether each module ships a small contracts-only NuGet package or
   whether installation creates an aggregate owner/revision contract pack. Exact package identity
   must remain authoritative either way.
4. **File-app SDK surface:** `#:include`/raw DLL and experimental `#:ref` behavior is moving across
   SDK feature bands. Pin the SDK and avoid those mechanisms until their public contract is stable.
5. **Native launcher:** creating an unpackaged AppContainer/LPAC is native Win32 work; prototype the
   trusted launcher and its pipe ACL before treating this as implemented architecture.
