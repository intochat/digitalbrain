# Persistence audit and proposed neuron-first migration

Source audit on 2026-09-28. Settings implementation committed as `402467575`. The proposal below was approved and implemented; see [implementation and rollout](2026-09-28-persistence-implementation.md). No live secret values or browser data were read, and no production data was deleted.

## Target

All durable application state is owned by account/workspace-scoped neurons and persisted through Orleans to the existing Azure Blob/Azurite provider. Flutter holds a disposable in-memory projection. No browser or host filesystem fallback may become an alternative source of truth. Explicit imports/exports and disposable execution files remain possible. Azurite itself necessarily stores its blobs in its persistent Docker volume; that is the intended backing store.

## Existing provider and first prerequisite

- [DigitalBrainHostingExtensions.cs](../../src/Modules/DigitalBrain/Kernel/DigitalBrain.Aspire.Hosting/Brain/DigitalBrainHostingExtensions.cs) already configures an Azurite emulator, persistent volume outside tests, Blob grain state via `WithGrainStorage("Default", grainState)`, and separate Azure Tables for clustering/reminders.
- [DigitalBrainRuntimeHostingExtensions.cs](../../src/Modules/DigitalBrain/Kernel/DigitalBrain.Aspire/DigitalBrainRuntimeHostingExtensions.cs) registers the Orleans serializer and container `digitalbrain-v2-state`.
- **Fix storage identity before migration:** [AppHost.cs](../../src/Applications/IntoChat/AppHost/AppHost.cs) generates a random development ClusterId when none is configured, then assigns that same value to ServiceId. This is a code-path finding, not proof of the currently configured runtime value. ServiceId must be a stable logical application identity; ClusterId can remain deployment-specific. Preserve/map existing state namespaces before changing this value. [Official Orleans guidance](https://learn.microsoft.com/en-us/dotnet/orleans/host/configuration-guide/server-configuration) explicitly requires stable ServiceId for persistence providers.

Implementation verification refined this finding: the configured Orleans Azure Blob provider's [GetBlobName implementation](https://github.com/dotnet/orleans/blob/v10.2.0/src/Azure/Orleans.Persistence.AzureStorage/Providers/Storage/AzureBlobStorage.cs) uses grain type and grain ID, not ServiceId. The existing `digitalbrain-v2-state` container and blob names remain unchanged. Azure Table reminder identity does use ServiceId: explicitly configured historical IDs are retained; reminders created under an old random deployment ID need re-registration by their owning module.

## Other durable stores relevant to a strict Orleans-only target

- **Compute PostgreSQL is active in normal AppHost**, not the file fallback: [AppHost.cs](../../src/Applications/IntoChat/AppHost/AppHost.cs) provisions a dedicated database and volume; [WalletNeuron.cs](../../src/Modules/DigitalBrain/Compute/DigitalBrain.Modules.Compute/Ledger/WalletNeuron.cs) delegates storage to ILedgerStore. Move immutable ledger/meter entries and idempotency keys into partitioned neurons if removing PostgreSQL is part of the target. Preserve atomic debit/credit, exactly-once operation semantics and summary reconciliation; a mechanical adapter replacement is insufficient.
- **Memory text and vectors are in Qdrant**: [MemoryNeuron.cs](../../src/Modules/Memory/DigitalBrain.Modules.Memory/DigitalBrain.Modules.Memory/MemoryNeuron.cs) persists counters in grain state but writes actual text/tags/payload/embedding to [QdrantVectorMemoryStore.cs](../../src/Modules/Memory/DigitalBrain.Modules.Memory/DigitalBrain.Modules.Memory/QdrantVectorMemoryStore.cs). Persist authoritative memory entries in neurons, with a replayable index outbox. Qdrant can remain rebuildable search infrastructure. Removing even that index requires a separate search implementation and trade-off.
- ClickHouse and customer Supabase are data-source integrations, not Flutter preference storage. Migrating customer databases into grain state is a separate product/data migration; do not silently change them.

## Already neuron-owned; preserve and extend

Identity directory and grants, connector records and encrypted secrets, app/package revisions and installed settings, C# source/settings, image edit recipes, workspace neuron references, assistant runs/conversation turns, token usage, and allowances already use PersistentState with the Default provider. A class named Neuron does not itself guarantee every byte is in grain persistence: Wallet and Memory above are counterexamples.

## Files that are not durable application state

- [SandboxRuns.cs](../../src/Modules/Microsoft/CSharp/DigitalBrain.Modules.Microsoft.CSharp.Sandbox/SandboxRuns.cs) materializes app.cs/build props to execute persisted C# source. Keep a disposable scratch directory, reconstruct from the CSharpFileNeuron; no recovery may depend on it.
- [FoundryLocalTranscriptionService.cs](../../src/Modules/AI/DigitalBrain.Modules.AI/Voice/FoundryLocalTranscriptionService.cs) and [OggOpusToWavConverter.cs](../../src/Modules/AI/DigitalBrain.Modules.AI/Voice/OggOpusToWavConverter.cs) use temporary audio files. Keep bounded lifetime/cleanup; stream where the engine supports it. Retained recordings would become assets.
- [SolutionWorkspace.cs](../../src/Modules/Microsoft/Roslyn/DigitalBrain.Modules.Microsoft.Roslyn/Workspace/SolutionWorkspace.cs) and its watcher intentionally edit an external developer checkout. That is a user-selected repository, not a hidden app-state store; keep as an explicit integration or remove that capability separately.
- Shipped package manifests/prompts are embedded assembly resources ([ShippedApps.cs](../../src/Applications/IntoChat/IntoChat/Marketplace/ShippedApps.cs)); package revisions already persist in neurons. Build assets, tests, logs, model downloads and Ollama model volumes are deployment/execution artifacts. Do not upload all of them into grain state.
- Authentication cookies are session credentials, not a competing app-state database. Browser cookie persistence can remain; native session state can remain in memory.

## Proposed implementation order

1. Stabilize ServiceId/container and protection-key identity. Add restart and fresh-client recovery tests before changing application ownership.
2. Add missing scoped preference, workspace presentation, conversation metadata/draft and paged transcript state. Reuse existing identity/workspace/assistant neurons. All commands carry operation ID and expected revision; only mark saved after successful durable acknowledgement. Never persist a giant workspace JSON blob as the replacement.
3. Implement a versioned, idempotent import from the current browser/device snapshot. Attribute it to the signed-in account, preserve stable IDs, reconcile existing server turns and handle collisions explicitly. Do not erase source data until server counts/digests and a durable migration marker agree. Other devices may still need to import their own old data.

   Read the raw snapshot before current load normalization clears window state or prunes references. Enumerate projects/conversations from the server before subscribing: today controllers only know locally listed projects, and chat restoration requires a locally remembered thread ID. Preserve unresolved old drafts and malformed records rather than overwriting them with a fresh empty snapshot.
4. Move assets and image save journals to neuron-owned Blob references. Use staged immutable uploads then commit references; clean orphan uploads separately. For literal all-bytes-through-Orleans semantics use bounded asset-chunk grains, but direct immutable Blob payloads owned by an asset neuron avoid rewriting large state and are the recommended binary design.
5. Replace Compute file/PostgreSQL/volatile stores according to the strictness chosen, preserving financial and paging guarantees; persist memory entries and make vector search rebuildable.
6. Remove SharedPreferences workspace writes, local receipt fallback and host-file recovery paths after successful migration. Keep only transient memory while offline; a closed offline client cannot recover unsent work without persistent local storage. Show unsaved/offline status clearly.
7. Prove the target: second browser sees the same workspace; browser app storage can be cleared; server restarts with empty scratch/assets directories but the same Azurite volume; interrupted migrations/uploads retry without duplication; two clients conflict safely; unauthorized workspaces cannot be read; all document bytes and conversation history recover.
