# AI, Supabase and UI E2E research

Date: 2026-09-20. Design research only; no implementation or tests executed. Context7 library resolution for Microsoft.Extensions.AI and Supabase returned monthly quota exceeded, so official documentation and repository source were used.

## What exists

- `src/Modules/AI/AI/Agents/AgentNeuron.cs`: `Ask` resolves the host `IChatClient`, creates a `ChatClientAgent`, and publishes `AgentReplied`. Its `ChatOptions` contains instructions only: this path currently supplies no tools. A test calling `IAgent.Ask` cannot demonstrate a Supabase tool round trip without production capability work.
- `src/Modules/AI/AI/Providers.cs`: unspecified provider/model resolves the default DI `IChatClient`; explicit provider/model creates a selected real provider pipeline. `src/Modules/AI/Tests/Agents/AgentFacts.cs` already substitutes a fixed `IChatClient` for a unit test. Retain that lightweight seam for unit tests.
- `src/Modules/AI/AI/Clients/LlmProviderFactories.cs`: `OpenAICompatibleProviderFactory` already honors `configuration.Provider(Provider).Endpoint`, constructs the real SDK client, and adapts `GetChatClient(model).AsIChatClient()`. Prefer a local scripted HTTP model endpoint for browser E2E: this retains the production factory and invocation pipeline without requiring test-assembly loading in the runtime. `src/Modules/AI/AI/AIModule.cs` currently omits provider endpoints from `Define`'s public settings projection; the proposed composition must carry that setting. Supply only a synthetic key through the private credential channel.
- `src/Modules/AI/AI/Clients/AIClients.cs`: real clients use `ChatClientBuilder.UseFunctionInvocation()`. A scripted client must return actual function-call content and inspect the resulting function results, rather than return an answer or call the database itself. Ensure exactly one layer owns tool invocation; retain the production agent's behavior when replacing the model boundary.
- `src/Modules/AI/AI/ConversationalAgent.cs`: contains instructions and requested native tool names `supabase_schema`, `supabase_query`, `show_supabase_query_table`. Repository-wide C# search finds these names only in that file: no current registrations were found. `src/Modules/AI/Contracts/NativeTools.cs` silently ignores unavailable names. Merely enabling AI and Supabase modules therefore does not establish this capability.
- `src/Applications/IntoChat/IntoChat/IntoChat.csproj`: old `ConversationalAgentEndpoints.cs`, workspace artifact tools and other HTTP endpoints are explicitly excluded from compilation. `Program.cs` exposes module surfaces and behaviors. The old conversation implementation is not proof of an active browser-to-agent path.
- `src/Modules/Supabase/Supabase/Query/SupabaseProvider.cs`: actual provider uses Npgsql and PostgreSQL SQL for schema, queries, paged tables and health. It runs read-only transactions and bounded queries. This is not a REST/PostgREST provider.
- `src/Modules/Supabase/Aspire.Hosting/SupabaseHostingExtensions.cs`: `WithSupabase` currently references an externally configured connection string; it does not provision a local database. `src/Modules/Supabase/Supabase/Configuration/SupabaseModuleOptions.cs` resolves the named private connection string. Current tests under `src/Modules/Supabase/Tests` use `FakeSupabaseProvider`; they do not validate the driver/database boundary.

## Primary-source implications

`FunctionInvokingChatClient` processes `FunctionCallContent` returned by its inner client, invokes the registered `AIFunction`, then supplies `FunctionResultContent` back to that client. This makes the inner model boundary a useful deterministic substitute while preserving real tool execution. [Microsoft API documentation](https://learn.microsoft.com/en-us/dotnet/api/microsoft.extensions.ai.functioninvokingchatclient?view=net-10.0-pp), [IChatClient guide](https://learn.microsoft.com/en-au/dotnet/ai/ichatclient).

Supabase supports direct PostgreSQL connections as well as other connection modes. Its local CLI runs the wider stack including PostgreSQL, Auth and Storage. Thus a local PostgreSQL test exercises this repository's current database integration, while a full local Supabase stack is appropriate when Supabase-specific services become part of the exercised path. [Database connections](https://supabase.com/docs/guides/database/connecting-to-postgres), [Local development](https://supabase.com/docs/guides/local-development). CLI migrations and seed data can make a dedicated local Supabase fixture reproducible. [Local workflow](https://supabase.com/docs/guides/local-development/cli-workflows).

## Recommended test contract

1. Default CI scenario: real application runtime, real browser/Flutter UI, production model factory, agent and tool dispatcher, real Supabase Npgsql provider, fresh disposable PostgreSQL database with deterministic seed rows. Substitute only the remote model endpoint with a local scripted HTTP server configured through the existing provider endpoint option. Implement its minimal response protocol against the repository's installed SDK and verify the actual request/response contract; this research does not claim a specific wire schema.
2. Start from a visible user prompt. Script schema discovery first, then a query-table tool call using the discovered schema. Require the second model turn to contain the real tool result; fail if expected functions are missing or arguments/results are inconsistent. Do not have the fixture create the UI table or directly call the provider on the agent's behalf.
3. The selected UX is a separate workspace window containing an interactive table. Assert its title, columns and distinct seed row values, with a value generated per test run so hardcoded answers cannot satisfy the test. Verify table filters and sorting cause the expected real result change. The proposed `IWorkspace` neuron should reference the existing Supabase table capability; tool completion alone is insufficient.
4. Include a focused failure case: database unavailability or invalid query yields a clear user-visible error and no fabricated result table. Preserve readiness stage, tool trace and screenshot artifacts on failure, excluding secrets.
5. Keep an opt-in live-model scenario against the same seeded local database and tool contract. It validates model selection/tool use but is inherently a different guarantee from the deterministic regression. Require semantic UI assertions rather than exact prose. Live cloud Supabase can be a separate opt-in environment validation if desired; do not mix it into the default reproducible suite.

The CI test should be described truthfully as application E2E with a deterministic model and real PostgreSQL-backed Supabase provider. It does not establish that an external LLM reliably understands arbitrary prompts, nor does it test Supabase Auth, REST authorization or realtime services.

## Capability work before the scenario can pass

Define a production tool capability shared by the actual user-facing agent path, with schema/query/table operations and explicit enablement. Provide an actual browser submission-to-agent route and a typed result-to-workspace projection. Carry the typed provider endpoint through module composition so the existing production factory can reach the scripted HTTP model server. Add isolated database provisioning/seeding plus private connection-reference injection. These are missing product/integration connections, not only test-harness syntax changes.
