# Milestone 2 Analysis: Roslyn Runtime Scripting & Mock LLM Stubs

## Executive Summary
Milestone 2 establishes robust in-memory scripting execution, validation, and deterministic mock LLM stubs for offline scenario validation and test-driven cycles. 

Our investigation confirms that:
1. **Dynamic Compilation:** Both full-class assembly generation (via `CSharpCompilation.Create` in `ImplCompileStage` / `StepCompileStage`) and script-based compilation (via `CSharpScript.Create` in `DynamicNeuronGrain` / `RoslynCompiler`) are already successfully in use inside the workspace. The scripting dependencies are pinned to version `5.0.0` to maintain compatibility with Orleans 10.1 workspaces.
2. **Mock LLMs:** `BddMockChatClient` and `MockChatClientAutoPrimer` provide a mature fingerprinting mechanism (generating 16-char lowercase SHA256 hashes of system + user chats) that automatically primes mocks from embedded `.feature` files at silo startup.
3. **Scripting Service:** The unified **Dynamic Scripting Service** contract `Task<ScriptResult> CompileAndExecuteAsync(string code, ExecutionContext context, CancellationToken ct)` is defined in `PROJECT.md` but is not yet fully implemented as a reusable SDK-level service.

This document details the exact technical mappings and provides a step-by-step implementation strategy for the worker to implement this service and construct mock LLM stubs for offline testing.

## 1. Dynamic Compilers, Script Managers, and Execution Engines
### 1.1 In-Tree Compilers
We located four major compiling and execution components across the workspace:
* **`InoCompiler.cs`** (`inolang/DigitalBrain.InoLang/InoCompiler.cs`):
  * **Role:** Compile InoLang script files (`.ino`) first-class.
  * **Chain:** `Lexer` -> `Parser` -> `Linker` -> `Lowering` -> `ExecutionPlan`.
  * **Gating:** Supports runtime scenario validation through `InoGate.EvaluateAsync(plan, ct)` which executes tests against a clean `StubSeamHost` before promotion.
* **`RoslynCompiler.cs`** (`kernel/BrainOS.Core.Hosting/RoslynCompiler.cs`):
  * **Role:** Performs compile-time syntax and type checks on C# script source strings generated by LLMs before staging them in the neuron registry.
  * **Engine:** Uses `CSharpScript.Create<string>(scriptSource, ScriptOptions.Default.WithReferences(...).WithImports(...), globalsType: typeof(DynamicNeuronScriptGlobals))` and returns plain-text diagnostics to the caller.
* **`DynamicNeuronGrain.cs`** (`kernel/BrainOS.Core.Hosting/DynamicNeuronGrain.cs`):
  * **Role:** Durable virtual actor (`IDynamicNeuron`) executing dynamic neuron scripts.
  * **Engine:** On `OnActivateAsync` or `LoadAsync`, it compiles the C# script via `CSharpScript.Create`. On `InvokeAsync`, it runs the compiled script in-memory with custom globals passing payload and system context.
* **`ImplCompileStage.cs` and `StepCompileStage.cs`** (`kernel/BrainOS.Kernel/Creator/`):
  * **Role:** Verify dynamically authored C# implementation libraries and custom Reqnroll step files generated by Creator loops.
  * **Engine:** Uses `CSharpCompilation.Create` with `CSharpSyntaxTree.ParseText` and references all loaded dynamic assemblies to compile dynamically linked libraries (`OutputKind.DynamicallyLinkedLibrary`) in memory.

### 1.2 Package and Assembly References
* **NuGet Packages:** Centrally managed in `Directory.Packages.props` and pinned to matching versions:
  * `<PackageVersion Include="Microsoft.CodeAnalysis.CSharp.Scripting" Version="5.0.0" />`
  * `<PackageVersion Include="Microsoft.CodeAnalysis.CSharp" Version="5.0.0" />`
* **Referenced Assemblies inside CSharpScript:**
  * `typeof(Neuron).Assembly` (BrainOS core neuron base class definitions)

* **Default Script Imports:**
  * `"System"`, `"System.Linq"`, `"System.Text.Json"`, `"System.Threading.Tasks"`, `"BrainOS.Core"`, `"Microsoft.Extensions.DependencyInjection"`

## 2. LLM Mock Stubs & Auto-Priming (`BddMockChatClient`)
### 2.1 Prompt Fingerprinting and Mocking
`BddMockChatClient` (`sdk/DigitalBrain.SDK/Ai/Llm/BddMockChatClient.cs`) is a complete, custom implementation of `IChatClient` (from `Microsoft.Extensions.AI`) used to mock LLM models during testing and offline scenarios:
1. **Fingerprint Computation:** For a list of chat messages, it generates a lowercase 16-character hex hash:
   * It appends the message role, followed by `:` and message text, separated by `\n` for all messages.
   * It computes the `SHA256` hash of this compiled string.
   * It truncates the resulting hex representation to the first 16 characters.
2. **Canned Lookup:** If an identical message sequence is submitted, `GetResponseAsync` computes the fingerprint, looks up the primed canned value in the `_primed` dictionary, and returns it. If not found, a detailed `BddMockMissException` is raised showing the first 5 primed fingerprints.
3. **Canned Logic Bypasses:**
   * **Moderator panel/Planners:** If the system prompt contains `"moderator of a small expert panel"`, the mock bypasses fingerprint lookup. It extracts destination and duration days from the user message via regex: `@"User's goal:\s*Plan:\s*(?<dest>.+?)\s+for\s+(?<days>\d+)\s+days?"` and dynamically constructs a complete canned JSON weekly itinerary.
   * **Persona stubs:** If the system prompt contains `"speaking as"`, it returns a canned response suggesting activities are time-blocked.

### 2.2 Feature Extractors & Auto-Priming
* **Regex Extraction:** `BddMockChatClient` exposes regex match loops that scan Gherkin feature file text for examples:
  * **Standard:** `Given the mock returns "[response]" for "[prompt]"`
  * **Intent:** `Given the intent mock returns '[json]' for transcript "[prompt]"`
  * **Planner:** `Given the planner mock returns '[json]' for intent "[prompt]"`
* **Auto-Primer Hosted Service:** `MockChatClientAutoPrimer.cs` is a standard `IHostedService`:
  * It scans all loaded assemblies in the AppDomain at silo startup.
  * It extracts all Gherkin examples from embedded `.feature` resources.
  * It maps and primes these examples across all registered mock model IDs in `MockModelRegistry.LlmModelIds`.

## 3. In-Memory Scripting and Scenario Hookup to Orleans & Tests
### 3.1 Scenario Execution and Gating
In-memory InoLang scripts and dynamic neurons are evaluated through two primary execution layers:
1. **InoLang ScenarioRunner:** Evaluates scenario blocks declared inside `.ino` spec files.
   * Uses `StubSeamHost` to stub out any `neuron()` calls or SLM predicate functions (`given` returns...).
   * Execution is direct tree-walk inside `Interpreter.cs`, ensuring deterministic, offline checks.
2. **Orleans InterpretedNeuronGrain:** Bridges dynamic scenarios to the live actor cluster.
   * Uses `ProductionSeamHost` to route seam requests to actual Orleans actor grains.
   * Active gating is performed via `ScenarioRunner` when a new neuron descriptor is configured. If any scenario fails (returns red), `ConfigureAsync` refuses to activate the neuron.

### 3.2 Existing Scripting Tests
We identified several active test files exercising dynamic Roslyn script compilation or scenario runs:
* **`RoslynCompilerTests.cs`** (`kernel/BrainOS.Core.Tests/RoslynCompilerTests.cs`): Verifies basic compiler success and diagnostic aggregation on broken C# scripts.
* **`DynamicNeuronScriptTests.cs`** (`kernel/BrainOS.Core.Tests/DynamicNeuronScriptTests.cs`): Validates executing C# scripts in-memory using `CSharpScript.Create` and `RunAsync` with custom globals.
* **`CompileStageTests.cs`** (`kernel/BrainOS.Kernel.Tests/Creator/CompileStageTests.cs`): Validates dynamic assembly generation and error checking for generated C# steps.
* **`InterpretedNeuronGrainTests.cs`** (`kernel/BrainOS.Kernel.Tests/Runtime/InterpretedNeuronGrainTests.cs`): Tests that interpreted neurons reject activation on red scenarios.
* **`DigitalBrainTiers.Steps.cs`** (`UI/BrainOS.E2E.Tests/DigitalBrainTiers.Steps.cs`): An end-to-end integration step that compiles and runs a raw C# script dynamically in-memory.

## 4. Milestone 2 Implementation Strategy
To complete Milestone 2, the implementer needs to build the **Dynamic Scripting Service** contract, define the runtime types, and ensure mock LLM stubs return deterministic values.

### Step 1: Define Contracts in `DigitalBrain.SDK.Contracts`
Create `sdk/DigitalBrain.SDK.Contracts/Scripting/ScriptResult.cs` and `ExecutionContext.cs` to hold in-memory scripting data:

```csharp
namespace DigitalBrain.SDK.Scripting;

public sealed record ScriptResult(
    bool Ok,
    object? ReturnValue,
    IReadOnlyList<string> Diagnostics,
    Exception? Exception = null);

public sealed class ExecutionContext
{
    public Dictionary<string, object> Globals { get; } = new(StringComparer.Ordinal);
    public IServiceProvider Services { get; set; } = null!;
}

public interface IDynamicScriptingService
{
    Task<ScriptResult> CompileAndExecuteAsync(string code, ExecutionContext context, CancellationToken ct);
}
```

### Step 2: Implement DynamicScriptingService in `DigitalBrain.SDK`
Create `sdk/DigitalBrain.SDK/Scripting/DynamicScriptingService.cs` implementing in-memory Roslyn compilation and execution:

```csharp
using Microsoft.CodeAnalysis.CSharp.Scripting;
using Microsoft.CodeAnalysis.Scripting;
using Microsoft.CodeAnalysis;

namespace DigitalBrain.SDK.Scripting;

public sealed class DynamicScriptingService : IDynamicScriptingService
{
    public async Task<ScriptResult> CompileAndExecuteAsync(string code, ExecutionContext context, CancellationToken ct)
    {
        try
        {
            var options = ScriptOptions.Default
                .WithReferences(
                    typeof(DynamicScriptingService).Assembly,
                    typeof(System.Text.Json.JsonSerializer).Assembly,
                    typeof(System.Linq.Enumerable).Assembly)
                .WithImports(
                    "System",
                    "System.Linq",
                    "System.Text.Json",
                    "System.Threading.Tasks",
                    "Microsoft.Extensions.DependencyInjection");

            var globals = new DynamicScriptingGlobals(context.Globals, context.Services);

            var script = CSharpScript.Create<object>(code, options, globalsType: typeof(DynamicScriptingGlobals));
            
            var compileDiagnostics = script.Compile();
            var errors = compileDiagnostics
                .Where(d => d.Severity == DiagnosticSeverity.Error)
                .Select(d => d.ToString())
                .ToList();

            if (errors.Count > 0)
            {
                return new ScriptResult(false, null, errors);
            }

            var state = await script.RunAsync(globals, cancellationToken: ct);
            return new ScriptResult(true, state.ReturnValue, errors);
        }
        catch (CompilationErrorException cex)
        {
            return new ScriptResult(false, null, cex.Diagnostics.Select(d => d.ToString()).ToList());
        }
        catch (Exception ex)
        {
            return new ScriptResult(false, null, new[] { ex.Message }, ex);
        }
    }
}

public sealed class DynamicScriptingGlobals(IReadOnlyDictionary<string, object> globals, IServiceProvider services)
{
    public IReadOnlyDictionary<string, object> Globals { get; } = globals;
    public IServiceProvider Services { get; } = services;
}
```

### Step 3: Wire Up Dependency Injection
Register the service in the SDK setup (e.g. in `sdk/DigitalBrain.SDK/Ai/BrainOSAiBridge.cs` or an appropriate SDK startup registry):
```csharp
builder.Services.AddSingleton<IDynamicScriptingService, DynamicScriptingService>();
```

### Step 4: Validate via Tests
Create unit tests under `sdk/DigitalBrain.SDK.Ai.Tests/` or another SDK test project:
1. Verify that a simple mathematical script evaluates correctly.
2. Verify that compile syntax/semantic errors are successfully captured in `Diagnostics`.
3. Verify that accessing `Globals` and `Services` in a C# script executes properly.
